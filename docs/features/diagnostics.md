# Diagnostics and troubleshooting tools

Playback fixer, predictions, test plays and the TV check, reports, server settings, library health, stats, speed check and the query analyzer.

Read CLAUDE.md first: its rules (keys, ids, privacy, licences, focus, server load) apply here too.

- Playback fixer: core `playback/PlaybackDoctor` turns a `PlaybackPlan` (server transcode reasons, `versions` with how each plays), the device caps and `PlaybackSettings` into plain findings with `PlaybackFix`es (another version/track, a `SettingsChange`, retry). In the player `PlaybackSession.diagnosis`/`applyFix` (re-asks the server from the same spot; a transcode stays forced only when Nitrate forced it after a failure); before playing `AppContainer.checkPlayback`/`applyPlaybackFix` (settings and versions only). TV: player "Why converting?" and details "How it plays"; phone: player Info → "Why converting?" and details "How it plays". Both also show "On this device", a fuller prediction (no badges anywhere else): core `jellyfin/ProfileCheck` evaluates the same `JellyfinDeviceProfile` Jellyfin would (containers, codecs, codec-profile conditions incl. `MediaStream.isInterlaced`/`dvProfile`, bitrate, subtitle burn-in, failed titles) into a `DeliveryVerdict` (a tone-mapped HDR picture names its real cause per format, `rangeReason`: set to Never, turned off after failures, or not reported by the display), and `playback/PlaybackPredictor` turns it into a `PlaybackPrediction` (delivery, decoder tier, HDR path, sound route, refresh plan from `AppPlatform.displaySnapshot()` (TV only), subtitles, what the device check saw; `rows()`), attached to `PlaybackDiagnosis.prediction` by `AppContainer.checkPlayback` (`predictPlayback` for any source).
- Device check (TV Settings → Playback test, `PlaybackTestScreen`): plays the sample clips once, recording decoder, whether each audio clip went out untouched (`onAudioTrackInitialized` encoding) and dropped frames, then times a refresh-rate switch (`FrameRateMatcher.refreshCheck`: black time, whether surround passthrough came back and when); saved per device as `PlaybackSettings.deviceCheck` (core `playback/DeviceCheck`, `CheckedClip`, `RefreshCheck`; backups keep it only on the same model) and quoted by predictions and the refresh plan.
- Library playback overview (Settings → Tools on both apps, `PlaybackOverviewScreen`/`PlaybackOverviewRoute`): every film and episode the user can see (`MediaServer.playbackSources(libraryId)`: `Items?fields=MediaSources`, paged by 300) run through `ProfileCheck.predict` (core `playback/PlaybackOverview`, `OverviewEntry`, `OverviewFilter` counts: plays as it is, repackaged, sound/picture converted, software decoded, surround decoded here); per library or all, each title opens its prediction; "Send to server log" (`AppContainer.sendPlaybackOverview`, `report()` with the device's deciding settings) so an admin can ask a user for it. Each title can be test played (`PlayerRoute(test = true)` on both Android apps, `canTestPlay` false on iOS): `TestPlay.PLAY_MS` (30 s) from `TestPlay.startAt` through the normal path, unreported like a recap clip (`loadClip`; no guards, Up Next, still-watching or SyncPlay), with the TV's refresh switch and passthrough as usual; the player hands a `TestPlayResult` (trail, dropped frames, error) to `AppContainer.saveTestPlay` (kept per account in `dataCache` "testplays", in the overview's report) and the overview shows it; "Test a sample" plays one title per kind of file (`TestPlay.sample` by `signature`: container, codec, size class, bit depth, HDR, interlacing, default sound, picture subtitles) one after another (route `queue`). The trail (core `playback/PlaybackTrail`, `TrailInput` → `Trail`s of `TrailStep`s with `TrailActor` and `differs`): picture (file, what Nitrate asked for with each HDR format's reason, the server's method and reasons in words, what arrived (measured MIME), decoder, Nitrate's processing, what went out, what to expect at the TV), sound, subtitles and refresh rate (display before vs now); `PlaybackSession.trail(caps)` builds it while playing, shown as "Path" in each player's Info (TV `TrailView` in `PlaybackInfoPanel`, phone `TrailView`) and in test results. HDR sent as is to a display Android says has no HDR reads "Sent as HDR. Android reports no HDR…" (`VideoPath.hdrUnreported`, in VideoPath, the trail and PlaybackPredictor), adding "but your TV showed it in the TV check" when `TvCheck.showedHdr`, and the tip to try Fire TV's Always HDR (other devices: always send HDR) if the picture looks dim: Fire OS gives apps no way to read its Dynamic Range setting, and Android doesn't say whether the device converts to SDR; never blamed on the server. Test plays (core-android `runTestPlay`, shared by both apps) play 10 s, jump ahead (`TestPlay.SEEK_AT_MS`/`SEEK_TO_MS`) to check seeking and that surround still goes out untouched, then play on to `END_MS`; the trail adds the server's own report while it converts (`MediaServer.serverConversion`: `Sessions?deviceId` TranscodingInfo → core `ServerConversion`, copied/converted, hardware, fps against the film: "can't keep up") and a Smoothness part (`Smoothness`: start-up to the first picture, stalls after it other than just after a seek, dropped frames, network against the stream, the seek). After a test the overview asks what only the user can see (`TestPlay.questions`: did the TV switch to HDR, did the receiver show the format; `Answer`, saved in `TestPlayResult.answers`) and `TestPlay.advice` turns answers and settings into `TestAdvice` (a `SettingsChange` applied in place, e.g. ForceAllow HDR when the TV showed it though Android reports none, or advice). TV & receiver check (TV Settings → Tools, `TvCheckScreen`; Companion feature `testclips`): the plugin carries ~20 s clips (`tools/generate-badge-clips.sh` → `companion/Nitrate.Companion/TestClips`, embedded, `/Nitrate/TestClips`; HDR10, Dolby Vision 8.1 and 5, HLG; Dolby Digital, DD+, TrueHD, DTS 5.1 and 7.1 PCM naming each speaker as it plays), played full screen one by one with "Did the TV/receiver show it?"; answers per device in `DeviceCheck.seen` (`SeenClip`, with passthrough and Android's HDR at the time), quoted by How it plays (`TvCheck.quoted`) and turned into settings (`TvCheck.advice`). Household devices (Companion feature `devices`; admins, Settings → Tools on both apps, `HouseholdDevicesScreen`): every device sends its own `DeviceSummary` (overview counts and converted titles, deciding settings, Android's HDR, test plays with answers, TV check) via `AppContainer.shareWithAdmin` a few seconds after its overview is read, a test play or a TV check answer (`PlaybackSettings.shareWithAdmin`, per device, on; a chip on the overview turns it off); the plugin keeps the latest per person and device (`Devices/DeviceHub`, opaque JSON, 512 KB, 200 reports) for admins; `Household.mostConverted` lists titles converted on several devices first. The guide to all of this is core `help/PlaybackGuide` ("Checking how things play", `GuideSection`s, `sectionsFor(tv, admin)` leaves out TV-only and admin parts), Settings → Tools first on both apps (`GuideScreen`), followed by "Advanced playback settings" (a link to Picture & sound → Advanced, which the tools' fixes change); keep it in step when a tool changes. TV choices, confirmations and short forms open as a side panel down the right edge, full height, the page still in view beside it under a light shade (`lists/TvDialog`, sliding in through `SidePanel`; `width` is the panel's width, never more than the screen less 80 dp; focus stays in it, Back closes it); `TvPanel` is the same frame for contents that arrange and scroll themselves (track lists, playback fixes, Add to, the A–Z filters); full-screen things (previews, ambient, readers, the person card over the video) keep their own `Dialog`; `TvDialog` scrolls its contents, so a `LazyColumn` (or a screen built on one, like `HomeSetupScreen`) inside it needs a set height, or open it in a plain fixed-size `Dialog` (Customize → Tabs); long text in a TV dialog goes in `ScrollBox` (focusable, ▲▼, buttons after it) so focus landing on the buttons never scrolls it out of reach.
- Playback reports: core `playback/PlaybackReport` renders device caps, what Nitrate allows, the item's streams, the server's decision and `PlaybackSession.eventLog()` (last 300 player events) as text, with tokens stripped from URLs; `AppContainer.sendPlaybackReport` saves it on the user's Jellyfin as a client log (`POST /ClientLog/Document`, shown under Dashboard → Logs). TV: player Send log and Playback settings → Send device report; phone: player Info → Send log / Share and Settings → Send device report.
- Media info (troubleshooting, phone): core `playback/MediaInfo` renders the file, every stream, the server's picks for the user (`MediaSource.defaultAudioIndex`/`defaultSubtitleIndex`/`defaultsKnown`, from the item's media source) and, while playing, the player's tracks, what's on, how subtitles are drawn and what a download's ASS files hold (`PlaybackSession.mediaInfo`); `MediaInfoDialog` (copy button) from How it plays and the player's Info. Downloads keep the server's picks and start with them (core `DownloadTracks.pick`; older downloads learn them via `withServerDefaults`), and the show's remembered languages win as when streaming.
- Server-side settings (troubleshooting): `MediaServer.serverSettings` (`Users/Me` Configuration and Policy, `System/Info/Public`, library names from `UserViews?includeHidden`) built by `jellyfin/JellyfinServerSettings` into core `account/ServerSettings` groups, each setting marked `SettingReach` (applies in Nitrate / Jellyfin's own apps only / reference) with where to change it; phone Settings → Account → Server-side settings (copy), TV Settings → Server-side settings (copy, save to server logs). For admins also "Converting on the server" (`System/Configuration/encoding`, `JellyfinServerSettings.converting`): hardware acceleration and decoding (10-bit HEVC), tone mapping and its algorithm/mode/desaturation/peak, Intel VPP, HEVC encoding, preset, each with a note and "Check:" where it explains washed-out HDR or slow converting. Also the Nitrate Companion plugin (core `account/CompanionStatus`, added by `JellyfinClient.serverSettings`): installed and answering / not installed / not answering, its version, each known feature on or off, spoken lines indexed (`/Nitrate/Lines/Status`), and features newer than the app. Read-only.
- Library health (admins, Settings): `MediaServer.healthScan(libraryId)` reads movies and shows with artwork, `Overview`, `ProviderIds` and every file's streams (episodes per show), plus `isMissing` episodes; core `diagnostics/LibraryHealth.findings` sorts them into `HealthCheck`s (always converted on this device via `CapabilityRules`, duplicate copies by name + year, missing artwork, not identified, missing description, missing episodes) with `HealthFix`es; `AppContainer.checkLibraryHealth`/`applyHealthFix` (refresh missing metadata/images, `mergeVersions` = `Videos/MergeVersions`); Identify opens Manage, "How it plays"/Open the details page. Each app has a `LibraryHealthScreen`.
- Watching stats ("Your year", Settings on both apps): `MediaServer.watchHistory` (finished films, episodes and songs with `UserState.lastPlayedMs`/`playCount`, paged) through core `stats/WatchStatsBuilder` (per year in the device's time zone, or all time; Jellyfin keeps only the last play date, so a title counts in that year and time counts every play): totals, month by month, top shows, genres, rewatched films, artists. Phone `StatsScreen`, TV `settings/StatsScreen`.
- Server speed check: `MediaServer.speedCheck` (JellyfinClient: `System/Ping`, `Users/Me`, `UserViews`, a recursive `Items` search, Home's row jobs each timed (`SpeedStep.parts`), `UserViews` again without plugin channels (`includeExternalContent=false`) to tell whether they make the library list slow, `Playback/BitrateTest` 2 MB, and decoding the search answer locally), each step repeated and judged on its median; core `diagnostics/SpeedCheck` rates steps and turns them into findings (network / server / device). `AppContainer.speedCheck`/`sendSpeedReport` (client log). TV: Settings → Server speed check; phone: Settings → Server speed check.
- The live connection (`JellyfinSocket.socketEvents`) backs off 2 s → 60 s between reconnects and starts over only once a connection has held 30 s: a server accepting and dropping it at once (as when a plugin broke its sessions) used to get a reconnect, and a Capabilities report, every 2 s from every device.
- Failed requests say why: the client records a refused request's status (`ResponseException`'s, since the response check throws before the interceptor sees it) and, with no answer at all, the error briefly (`QueryRecord.error`); each request group lists them (`QueryGroup.failures`, "403 ×18", "no answer (timeout) ×1") in the analyzer on both apps and its copied text. A details page's Watched or Favourite the server refuses says why under the buttons (`DetailsState.actionError`: "Couldn't mark it watched: the server said 403 Forbidden: …", `JellyfinClient.saying`); nothing on screen changes until the server has made the change.
- Query analyzer and shared answers: every request `JellyfinClient` makes passes its `HttpSend` interceptor, which times it (body included), tags it (`X-Nitrate-Query: <run>-<n>`, `QueryLog.nextTag`) and adds a core `diagnostics/QueryRecord` to `MediaServer.queryLog` (`QueryLog`, newest 2,000; endpoint with ids as `{id}`, `shape` = endpoint + parameters without paging; long polls with `waitMs` left out) put down to the coroutine's `QueryOrigin` (`withQueryOrigin(part)` nests "Home › Next Up": `RowsViewModel` by `QueryLog.pageLabel(pageKey)`, `ProgressiveRows` by job name, custom rows by title, the view models, search, screensaver/channels/widgets, `AppContainer`'s background jobs). Lists of titles (`items()`) go through core `cache/AnswerCache`: keyed by account + URL (`answerKey`), single-flight (askers meanwhile JOIN the one fetch), kept per `AnswerKind` (Next Up/Resume 30 s, Latest 5 min, other lists 2 min, library list 5 min, Similar 1 h, `STRUCTURE` 6 h: a show's seasons, a season's episodes, a film's collections and their films, shared with the player's Next in collection); `UserDataChanged` carries each item's new `UserState` (`ServerEvent.UserDataChanged.states`), so lists whose titles follow watch state (`dependsOnWatchState`: Next Up/Resume and any request with `WATCH_STATE_FILTERS`) go and every other kept list has the marks patched in place (`AnswerCache.patch`; an event without states drops them all as before); anything this client sends (non-GET) drops only the watch-state lists; everything goes on `LibraryChanged`; lists that never show a total ask Jellyfin not to count (`COUNTING_LISTS` get `enableTotalRecordCount=false`; pictures aren't limited, since cards-hidden rows rotate every backdrop); with the Companion (`companionHas`, features asked at most every 5 minutes) Home's jobs first await one `/Nitrate/Home` (`homeBundle`, `RowJob.after`), whose lists are kept under the keys Home's own requests use (`keepList`, `AnswerCache.put`), "Because you watched" comes from `/Nitrate/Because` (no similar search, no device copy) and format filters read `/Nitrate/Formats` (`companionFormats`), each falling back to the usual requests; "Because you watched" is also single-flight. Shared answers are logged as JOINED/KEPT, so the analyzer shows what sharing saved. Core `QueryHints` (similar titles, sorting by date played, random, no limit, counting every match, full file details, slow, large) and `QuerySummary` (costliest shapes, by origin, repeats within a minute, `render` for the server log). Settings → Tools → Query analyzer on both apps (TV `settings/QueryAnalyzerScreen`, phone `QueryAnalyzerScreen`; admins also see "Across the household", `AppContainer.householdQueries`): Record a visit (`startRecording`/`stopRecording`, `QueryRecording.covers`), costliest, by page, latest, Save to server logs (`AppContainer.sendQueryReport`, ids named by `queryNames` via `QueryLog.readable`). With Companion feature `querytimes` (`QueryTimes/QueryTimingMiddleware` added through an `IStartupFilter`, `QueryTimeStore` per user in memory 2 h, `GET /Nitrate/QueryTimes?run=` the caller's own; the feature shows only once the middleware has seen a request) the server's own times are merged (`fetchServerQueryTimes`, `addServerTimes`).
