# Diagnostics and troubleshooting tools

Playback fixer, predictions, test plays and the TV check, reports, server settings, library health, stats, speed check and the query analyzer.

Read CLAUDE.md first: its rules (keys, ids, privacy, licences, focus, server load) apply here too.

- Playback fixer: core `playback/PlaybackDoctor` turns a `PlaybackPlan` (server transcode reasons, `versions` with how each plays), the device caps and `PlaybackSettings` into plain findings with `PlaybackFix`es (another version/track, a `SettingsChange`, Play original, Convert this time, Always convert here: `playback.md`). In the player `PlaybackSession.diagnosis`/`applyFix` (re-asks the server from the same spot; a transcode stays forced only when Nitrate forced it after a failure); before playing `AppContainer.checkPlayback`/`applyPlaybackFix` (settings and versions only). TV: player "Why converting?" (or "Stuttering? Convert" while a software-decoded format plays as it is) and details "How it plays"; phone: player Info → "Why converting?" and details "How it plays". Both also show "On this device", a fuller prediction (no badges anywhere else): core `jellyfin/ProfileCheck` evaluates the same `JellyfinDeviceProfile` Jellyfin would (containers, codecs, codec-profile conditions incl. `MediaStream.isInterlaced`/`dvProfile`, bitrate, subtitle burn-in) into a `DeliveryVerdict` (a tone-mapped HDR picture names its real cause per format, `rangeReason`: set to Server converts, or not reported by the display), and `playback/PlaybackPredictor` turns it into a `PlaybackPrediction` (delivery, decoder tier, HDR path, sound route, refresh plan from `AppPlatform.displaySnapshot()` (TV only), subtitles, what the device check saw; `rows()`), attached to `PlaybackDiagnosis.prediction` by `AppContainer.checkPlayback` (`predictPlayback` for any source).
- Device check (TV Settings → Playback test, `PlaybackTestScreen`): plays the sample clips once, recording decoder, whether each audio clip went out untouched (`onAudioTrackInitialized` encoding) and dropped frames, then times a refresh-rate switch (`FrameRateMatcher.refreshCheck`: black time, whether surround passthrough came back and when); saved per device as `PlaybackSettings.deviceCheck` (core `playback/DeviceCheck`, `CheckedClip`, `RefreshCheck`; backups keep it only on the same model) and quoted by predictions and the refresh plan. Software decoding is timed on the library itself: for each format with no hardware decoder here (`PlaybackTest.softwareOnly`: VC-1, MPEG-2… on a Fire TV Stick), the Companion names the hardest file the user can see (`MediaServer.heaviestFiles`, `GET /Nitrate/Formats/Heaviest`: most pixels a second, then the highest bit rate; no name, so no spoiler) and the check plays 20 seconds of it from a third of the way in (`PlaybackTest.librarySample`, `MediaServer.videoFileUrl`, a clipped `MediaItem`), counting only late frames (the ones decoded to reach the start are "skipped", not late); more than 2% dropped (`LIBRARY_MAX_DROPPED_SHARE`) is Too slow and suggests "Have the server convert [format] here" (`overrides[codec] = NEVER`). Kept as `deviceCheck.clips["library:<codec>"]`; Formats and the fixer quote it (`PlaybackTest.measured`).
- Library playback overview (Settings → Tools on both apps, `PlaybackOverviewScreen`/`PlaybackOverviewRoute`): every film and episode the user can see (`MediaServer.playbackSources(libraryId)`: `Items?fields=MediaSources`, paged by 300) run through `ProfileCheck.predict` (core `playback/PlaybackOverview`, `OverviewEntry`, `OverviewFilter` counts: plays as it is, repackaged, sound/picture converted, software decoded, surround decoded here); per library or all, each title opens its prediction; "Send to server log" (`AppContainer.sendPlaybackOverview`, `report()` with the device's deciding settings) so an admin can ask a user for it. Each title can be test played (`PlayerRoute(test = true)` on both Android apps, `canTestPlay` false on iOS): `TestPlay.PLAY_MS` (30 s) from `TestPlay.startAt` through the normal path, unreported like a recap clip (`loadClip`; no guards, Up Next, still-watching or SyncPlay), with the TV's refresh switch and passthrough as usual; the player hands a `TestPlayResult` (trail, dropped frames, error) to `AppContainer.saveTestPlay` (kept per account in `dataCache` "testplays", in the overview's report) and the overview shows it; "Test a sample" plays one title per kind of file (`TestPlay.sample` by `signature`: container, codec, size class, bit depth, HDR, interlacing, default sound, picture subtitles) one after another (route `queue`). The trail (core `playback/PlaybackTrail`, `TrailInput` → `Trail`s of `TrailStep`s with `TrailActor` and `differs`): picture (file, what Nitrate asked for with each HDR format's reason, the server's method and reasons in words, what arrived (measured MIME), decoder, Nitrate's processing, what went out, what to expect at the TV), sound, subtitles and refresh rate (display before vs now); `PlaybackSession.trail(caps)` builds it while playing, shown as "Path" in each player's Info (TV `TrailView` in `PlaybackInfoPanel`, phone `TrailView`) and in test results. HDR sent as is to a display Android says has no HDR reads "Sent as HDR. Android reports no HDR…" (`VideoPath.hdrUnreported`, in VideoPath, the trail and PlaybackPredictor), adding "but your TV showed it in the TV check" when `TvCheck.showedHdr`, and the tip to try Fire TV's Always HDR (other devices: always send HDR) if the picture looks dim: Fire OS gives apps no way to read its Dynamic Range setting, and Android doesn't say whether the device converts to SDR; never blamed on the server. Test plays (core-android `runTestPlay`, shared by both apps) play 10 s, jump ahead (`TestPlay.SEEK_AT_MS`/`SEEK_TO_MS`) to check seeking and that surround still goes out untouched, then play on to `END_MS`; the trail adds the server's own report while it converts (`MediaServer.serverConversion`: `Sessions?deviceId` TranscodingInfo → core `ServerConversion`, copied/converted, hardware, fps against the film: "can't keep up") and a Smoothness part (`Smoothness`: start-up to the first picture, stalls after it other than just after a seek, dropped frames, network against the stream, the seek). After a test the overview asks what only the user can see (`TestPlay.questions`: did the TV switch to HDR, did the receiver show the format; `Answer`, saved in `TestPlayResult.answers`) and `TestPlay.advice` turns answers and settings into `TestAdvice` (a `SettingsChange` applied in place, e.g. ForceAllow HDR when the TV showed it though Android reports none, or advice). TV & receiver check (TV Settings → Tools, `TvCheckScreen`; Companion feature `testclips`): the plugin carries ~20 s clips (`tools/generate-badge-clips.sh` → `companion/Nitrate.Companion/TestClips`, embedded, `/Nitrate/TestClips`; HDR10, Dolby Vision 8.1 and 5, HLG; Dolby Digital, DD+, TrueHD, DTS 5.1 and 7.1 PCM naming each speaker as it plays), played full screen one by one with "Did the TV/receiver show it?"; answers per device in `DeviceCheck.seen` (`SeenClip`, with passthrough and Android's HDR at the time), quoted by How it plays (`TvCheck.quoted`) and turned into settings (`TvCheck.advice`). Household devices (Companion feature `devices`; admins, Settings → Tools on both apps, `HouseholdDevicesScreen`): every device sends its own `DeviceSummary` (overview counts and converted titles, deciding settings, Android's HDR, test plays with answers, TV check) via `AppContainer.shareWithAdmin` a few seconds after its overview is read, a test play or a TV check answer (`PlaybackSettings.shareWithAdmin`, per device, on; a chip on the overview turns it off); the plugin keeps the latest per person and device (`Devices/DeviceHub`, opaque JSON, 512 KB, 200 reports) for admins; `Household.mostConverted` lists titles converted on several devices first. The guide to all of this is core `help/PlaybackGuide` ("Checking how things play", `GuideSection`s, `sectionsFor(tv, admin)` leaves out TV-only and admin parts), Settings → Tools first on both apps (`GuideScreen`), followed by "Advanced playback settings" (a link to Picture & sound → Advanced, which the tools' fixes change); keep it in step when a tool changes. TV choices, confirmations and short forms open as a side panel down the right edge, full height, the page still in view beside it under a light shade (`lists/TvDialog`, sliding in through `SidePanel`; `width` is the panel's width, never more than the screen less 80 dp; focus stays in it, Back closes it); `TvPanel` is the same frame for contents that arrange and scroll themselves (track lists, playback fixes, Add to, the A–Z filters); full-screen things (previews, ambient, readers, the person card over the video) keep their own `Dialog`; `TvDialog` scrolls its contents, so a `LazyColumn` (or a screen built on one, like `HomeSetupScreen`) inside it needs a set height, or open it in a plain fixed-size `Dialog` (Customize → Tabs); long text in a TV dialog goes in `ScrollBox` (focusable, ▲▼, buttons after it) so focus landing on the buttons never scrolls it out of reach.
- Who decodes, in one set of words everywhere (core `playback/Decoders`): this device's hardware, Android's software decoder (`c2.android.…`, `OMX.google.…`), Nitrate's FFmpeg (`ffmpeg6.0-<codec>` for sound, `nitrate.ffmpeg.<codec>`/"FFmpeg (software) <codec>" for the picture), or for sound "Sent untouched to the TV or receiver", each with the decoder's own name in brackets (`DecoderTier.plain`, `Decoders.describe`, `describeSound`, `describeReported` for what a device reports, e.g. Opus "… for stereo; Nitrate's FFmpeg for 5.1 and 7.1"). The player's Info (TV `PlaybackInfoPanel`, phone) starts with Server (`Decoders.serverWords`: Plays as it is, Repackaged, Converting the sound only (a conversion for sound reasons alone, the picture copied), Converting picture and sound), then Picture decoder and Sound decoder (`infoRows(…, soundPassedThrough)`); the trail's Decoded by steps (picture and sound) and the report's "Decoders in use" and per-format lines say the same; Settings' format lists (TV Picture & sound → Advanced, phone) say "decoded by …" per format (`Decoders.decodedBy`). Desktop and iOS mpv give the same rows from mpv's own properties (`MpvDecoding.read`: `hwdec-current`, `video-format`, `audio-codec-name`, `audio-out-params/format`; desktop `MpvPlayer.decoding()`, iOS `MpvPlayer.property` through the Swift player's `property(name:)`): "This computer's graphics card (d3d11va, hevc)" / "This device's hardware (videotoolbox, hevc)", "mpv's software decoder (FFmpeg, av1)", "mpv's FFmpeg (eac3)" or passed through ("spdif-…"); Apple's player names no decoder, so iOS says "Apple's player (iOS chooses the decoder)" (`Decoders.APPLE_PLAYER`); `infoRows(pictureWords, soundWords)` and, for a format not played as it is, "server converts the sound" or "server converts the picture" (`serverConverts`) in place of "transcode" (`DecodersTest`).
- Playback reports: core `playback/PlaybackReport` renders device caps, what Nitrate allows, the item's streams, the server's decision and `PlaybackSession.eventLog()` (last 300 player events) as text, with tokens stripped from URLs; `AppContainer.sendPlaybackReport` saves it on the user's Jellyfin as a client log (`POST /ClientLog/Document`, shown under Dashboard → Logs). TV: player Send log and Playback settings → Send device report; phone: player Info → Send log / Share and Settings → Send device report.
- Screen drawing in playback reports (TV player): core `playback/FrameStats`, held by `PlaybackSession.frames` and fed by the TV `PlayerScreen` from Android's per-frame timings (`Window.addOnFrameMetricsAvailableListener` on the main thread; the first frame left out), tallied by what was open (nothing, the controls up, More, Info, the chat, a pop-up or panel; kept in a plain holder, so measuring never redraws anything): frames, late ones (over one refresh at the screen's rate then, 41.7 ms at 23.976 Hz), those over 100 ms, a typical one and the worst. `PlayerReport.uiFrames` → the report's "Screen drawing" section, so a slow player menu can be told apart from a busy device (`FrameStatsTest`).
- Screen drawing across the app (TV): `AppContainer.screenDrawing`, a `FrameStats(prefix = "On")`, fed by `NitrateNavHost` from the window's frame timings (`addOnFrameMetricsAvailableListener`, first-draw frames left out, the player left to its own tally) tallied by screen (`screenName`: the route's class name without "Route"). `sendPlaybackReport` puts it in every device report ("Screen drawing across the app", `PlaybackReport.screenFrames`), so a slow page shows up by name. The player's Info panel works out its prediction off the main thread once per plan and settings (`PlaybackSession.trail`), rather than on the main thread every 2 seconds.
- Media info (troubleshooting, phone): core `playback/MediaInfo` renders the file, every stream, the server's picks for the user (`MediaSource.defaultAudioIndex`/`defaultSubtitleIndex`/`defaultsKnown`, from the item's media source) and, while playing, the player's tracks, what's on, how subtitles are drawn and what a download's ASS files hold (`PlaybackSession.mediaInfo`); `MediaInfoDialog` (copy button) from How it plays and the player's Info. Downloads keep the server's picks and start with them (core `DownloadTracks.pick`; older downloads learn them via `withServerDefaults`), and the show's remembered languages win as when streaming.
- Server-side settings (troubleshooting): `MediaServer.serverSettings` (`Users/Me` Configuration and Policy, `System/Info/Public`, library names from `UserViews?includeHidden`) built by `jellyfin/JellyfinServerSettings` into core `account/ServerSettings` groups, each setting marked `SettingReach` (applies in Nitrate / Jellyfin's own apps only / reference) with where to change it; phone Settings → Account → Server-side settings (copy), TV Settings → Server-side settings (copy, save to server logs). For admins also "Converting on the server" (`System/Configuration/encoding`, `JellyfinServerSettings.converting`): hardware acceleration and decoding (10-bit HEVC), tone mapping and its algorithm/mode/desaturation/peak, Intel VPP, HEVC encoding, preset, each with a note and "Check:" where it explains washed-out HDR or slow converting. Also the Nitrate Companion plugin (core `account/CompanionStatus`, added by `JellyfinClient.serverSettings`): installed and answering / not installed / not answering, its version, each known feature on or off, spoken lines indexed (`/Nitrate/Lines/Status`), and features newer than the app. Read-only.
- Library health (admins, Settings): `MediaServer.healthScan(libraryId)` reads movies and shows with artwork, `Overview`, `ProviderIds` and every file's streams (episodes per show), plus `isMissing` episodes; core `diagnostics/LibraryHealth.findings` sorts them into `HealthCheck`s (always converted on this device via `CapabilityRules`, duplicate copies by name + year, missing artwork, not identified, missing description, missing episodes) with `HealthFix`es; `AppContainer.checkLibraryHealth`/`applyHealthFix` (refresh missing metadata/images, `mergeVersions` = `Videos/MergeVersions`); Identify opens Manage, "How it plays"/Open the details page. Each app has a `LibraryHealthScreen`.
- Library images overview (admins with the Companion's `imagesurvey`, Settings → Tools on both apps, `ImagesOverviewScreen`/`ImagesOverviewRoute`; Settings search "Library images overview"): per library (films, shows, mixed, home videos, music videos, collections) or all, every film, show, season, episode, collection and video's pictures: total space, items and images, how many complete; per kind of picture (`ImageTypeTotals`: count, bytes, small, wrong shape, file gone, not saved on the server, size unknown); per kind of title (`ImageKindTotals`: count, complete, bytes, how many lack each expected kind); "To look at" (`ImageProblem`, filtered by `ImageFlawKind` Missing/Small/Wrong shape/File gone and by image type, re-asked of the server; at most 300 listed, the total counted), each opening Manage on Images (`ManageItemRoute(images = true)`) with "Find missing" (refresh, missing images only) when one is missing; "Fix these" runs through the titles listed (core `ImageFixRun.steps`: each `FixStep` the kind filtered by, else its first missing kind, else its first flawed; kept in `AppContainer.imageFixRun`, too long for a route, `ManageItemRoute(run = true)`): Manage opens each on Images with the found pictures of that kind already open and a bar "Fixing 3 of 24 · Show · S1E2 · logo" with Skip; placing a picture moves on to the next (`onPlaced`), and the last says all done; "Find missing · N" asks the server for missing pictures (missing only, never replacing) for every listed title missing one, one at a time with "Asking the server: 12 of 40", the ones asked dropped from the count; logos, clear art and discs that aren't see-through count as "No transparency" (`ImageFlawKind.OPAQUE`, `ImageTypeTotals.opaque`; the rule's `transparent` sent to the Companion, which reads those files' headers); the 20 biggest files. The rules are the app's (core `admin/ImageGuide`, sent with every ask): what each kind should have (films and shows a poster, backdrop and logo; seasons, episodes and collections a poster; other kinds are counted, never "missing"), and the size guide from `RemoteImages.spec` (small: narrower than "good"; wrong shape: more than 15% from `ImageSpec.ratio`; logos any shape; an episode's main picture is a 16:9 still, called "Still"). Episodes are named by show and number only ("Show · S1E2", `ImageGuide.title`: no spoilers). TV: selecting a kind of picture lists only its problems, a kind of title lists what's missing. Kept while the app runs (`AppContainer.lastImageOverview`). The server's resized copies (its image cache) and people's photos aren't counted. Server side: `docs/features/companion.md` (`POST /Nitrate/Images/Overview`). Tests: core `ImageOverviewTest`, Companion `ImageSurveyTests`, screenshots TV/phone `imagesOverview`, `imagesOverviewProblems`.
- Watching stats ("Your year", Settings on both apps): `MediaServer.watchHistory` (finished films, episodes and songs with `UserState.lastPlayedMs`/`playCount`, paged) through core `stats/WatchStatsBuilder` (per year in the device's time zone, or all time; Jellyfin keeps only the last play date, so a title counts in that year and time counts every play): totals, month by month, top shows, genres, rewatched films, artists. Phone `StatsScreen`, TV `settings/StatsScreen`.
- Server speed check: `MediaServer.speedCheck` (JellyfinClient: `System/Ping`, `Users/Me`, `UserViews`, a recursive `Items` search, Home's row jobs each timed (`SpeedStep.parts`), `UserViews` again without plugin channels (`includeExternalContent=false`) to tell whether they make the library list slow, `Playback/BitrateTest` 2 MB, and decoding the search answer locally), each step repeated and judged on its median; core `diagnostics/SpeedCheck` rates steps and turns them into findings (network / server / device). `AppContainer.speedCheck`/`sendSpeedReport` (client log). TV: Settings → Server speed check; phone: Settings → Server speed check.
- "Why is Watched slow?" (admins with the Companion, feature `watchtiming`; phone Settings → Tools beside the speed check, `WatchTimingRow`/`WatchTimingDialog`; TV at the bottom of the speed check page): for three minutes the server times the admin's own Watched/Unwatched presses, in any app, and each listener Jellyfin runs inside the save when a title's watch state changes (plugins such as Trakt, Webhook, Playback Reporting; Jellyfin's own, e.g. `NfoUserDataSaver` writing watch state into .nfo files next to the media when NFO saving of user data is on). Companion `WatchTiming/WatchChangeTiming` stands in for `IUserDataManager.UserDataSaved`'s listeners (reflection on the event's field), calls each in turn as Jellyfin would with a stopwatch on each (an async listener, such as `NfoUserDataSaver`, hands its work off at its first wait: only the part before holds the save up, and its name says "then carries on in the background"), keeps only the starting admin's saves (episodes by show and number only) and their `POST/DELETE /UserPlayedItems` times from the request timing (`CompanionLogic.RequestFinished`), and puts the listeners back (plus any added meanwhile) when it ends, when stopped, or first when the logic stops (registered last). `/Nitrate/WatchTiming` (`POST Start?minutes=`, `POST Stop`, `GET`), admins only. Core `diagnostics/WatchTiming` (findings: a listener over 100 ms named with how much it costs every save; else the rest is the database, or nothing is slow and it's the network), `MediaServer.startWatchTiming/watchTimingReport/stopWatchTiming`, `AppContainer.canTimeWatched`.
- The live connection (`JellyfinSocket.socketEvents`) backs off 2 s → 60 s between reconnects and starts over only once a connection has held 30 s: a server accepting and dropping it at once (as when a plugin broke its sessions) used to get a reconnect, and a Capabilities report, every 2 s from every device.
- Failed requests say why: the client records a refused request's status (`ResponseException`'s, since the response check throws before the interceptor sees it) and, with no answer at all, the error briefly (`QueryRecord.error`); each request group lists them (`QueryGroup.failures`, "403 ×18", "no answer (timeout) ×1") in the analyzer on both apps and its copied text. A details page's Watched or Favourite the server refuses says why under the buttons (`DetailsState.actionError`: "Couldn't mark it watched: the server said 403 Forbidden: …", `JellyfinClient.saying`); nothing on screen changes until the server has made the change.
- Query analyzer and shared answers: every request `JellyfinClient` makes passes its `HttpSend` interceptor, which times it (body included), tags it (`X-Nitrate-Query: <run>-<n>`, `QueryLog.nextTag`) and adds a core `diagnostics/QueryRecord` to `MediaServer.queryLog` (`QueryLog`, newest 2,000; endpoint with ids as `{id}`, `shape` = endpoint + parameters without paging; long polls with `waitMs` left out) put down to the coroutine's `QueryOrigin` (`withQueryOrigin(part)` nests "Home › Next Up": `RowsViewModel` by `QueryLog.pageLabel(pageKey)`, `ProgressiveRows` by job name, custom rows by title, the view models, search, screensaver/channels/widgets, `AppContainer`'s background jobs). Lists of titles (`items()`) go through core `cache/AnswerCache`: keyed by account + URL (`answerKey`), single-flight (askers meanwhile JOIN the one fetch), kept per `AnswerKind` (Next Up/Resume 30 s, Latest 5 min, other lists 2 min, library list 5 min, Similar 1 h, `STRUCTURE` 6 h: a show's seasons, a season's episodes, a film's collections and their films, shared with the player's Next in collection; `SEARCH` 1 min: quick matches, full results and spoken lines, the term trimmed, people taken from the quick matches rather than a `/Persons` search of their own; `COMPANION` 3 min: a show's group progress and the Companion's update status, let go by anything the app sends and by a watch change, group progress also when the groups change); `JellyfinClient.shared(kind, path, query) { … }` puts any GET through them; `UserDataChanged` carries each item's new `UserState` (`ServerEvent.UserDataChanged.states`), so lists whose titles follow watch state (`dependsOnWatchState`: Next Up/Resume and any request with `WATCH_STATE_FILTERS`) go and every other kept list has the marks patched in place (`AnswerCache.patch`; an event without states drops them all as before); anything this client sends (non-GET) drops only the watch-state lists; everything goes on `LibraryChanged`; lists that never show a total ask Jellyfin not to count (`COUNTING_LISTS` get `enableTotalRecordCount=false`; pictures aren't limited, since cards-hidden rows rotate every backdrop); with the Companion (`companionHas`, features asked at most every 5 minutes) Home's jobs first await one `/Nitrate/Home` (`homeBundle`, `RowJob.after`), whose lists are kept under the keys Home's own requests use (`keepList`, `AnswerCache.put`), "Because you watched" comes from `/Nitrate/Because` (no similar search, no device copy) and format filters read `/Nitrate/Formats` (`companionFormats`), each falling back to the usual requests; "Because you watched" is also single-flight. Shared answers are logged as JOINED/KEPT, so the analyzer shows what sharing saved. Core `QueryHints` (similar titles, sorting by date played, random, no limit, counting every match, full file details, slow, large) and `QuerySummary` (costliest shapes, by origin, repeats within a minute (the very same request, `QueryRecord.request`: another title's lookup of the same shape isn't one), `render` for the server log). Settings → Tools → Query analyzer on both apps (TV `settings/QueryAnalyzerScreen`, phone `QueryAnalyzerScreen`; admins also see "Across the household", `AppContainer.householdQueries`): Record a visit (`startRecording`/`stopRecording`, `QueryRecording.covers`), costliest, by page, latest, Save to server logs (`AppContainer.sendQueryReport`, ids named by `queryNames` via `QueryLog.readable`). With Companion feature `querytimes` (`QueryTimes/QueryTimingMiddleware` added through an `IStartupFilter`, `QueryTimeStore` per user in memory 2 h, `GET /Nitrate/QueryTimes?run=` the caller's own; the feature shows only once the middleware has seen a request) the server's own times are merged (`fetchServerQueryTimes`, `addServerTimes`).
- "Nitrate closed unexpectedly" (Android, both apps): core-android `CrashNote` (installed in each app's `Application`) writes an error nothing caught to `last-crash.txt` in the app's files folder as the app closes (still closing as before; never sent anywhere). Settings → Tools then shows a line for it (phone `LastCrashRow`: read it, Copy, Save in server logs, Forget; TV: Save in server logs, which forgets it once saved), through `AppContainer.lastCrash`/`sendLastCrash`/`clearLastCrash` (`sendClientLog`, the user's own server).
- The last playback's log (Android, both apps): `PlaybackSession` keeps its report (the device, the server's decision, the player's events, the error) on the device every 10 s while playing, off the main thread so a playback whose screen stops answering is still on record, and when it closes (a player error is logged with where it happened: the innermost cause's first stack frames, plus Nitrate's first frame when those are all Media3's; `whereFailed`) (`keepLog` → `AppContainer.keepPlaybackLog`, `last-playback.txt` with the title's id; test plays and clips aren't kept). How it plays on that title's details page then offers "Send the last try's log" (`sendLastPlaybackLog`: the user's own server's logs, Jellyfin Dashboard → Logs). Nothing is sent unless asked.
- Dolby Vision profile 7 in the playback test (TV Settings → Playback test only, not the one-time device check): `PlaybackTest.profile7Clips` plays MEL and FEL clips (`dv_p7_mel_2160p.mkv`, `dv_p7_fel_2160p.mkv`: bundled, single-track MKV as disc copies are) each converted to 8.1 and as its HDR10 base layer (and as Dolby Vision 7 itself where a decoder reports profile 7: `profile7Clips(heavy, native)`), through the same `DolbyVisionProfile7` handling as real playback (the test player's extractors; one player for every clip), and, when the Companion has it, the disc-like FEL clip (`dolby_vision_7_fel_heavy`: 40 Mbps, keyframes over 5 MB, about 28 MB, served from the plugin's clips with the sign-in header, given 60 s). After each profile 7 clip that showed frames it loops in the preview and the user is asked whether there's a picture (`PictureQuestion`, Yes takes focus, focus back to Stop after): decoders can turn out frames that are all black, as a FEL film was on a MediaTek box, so "No, it's black" makes it a failure (`sawPicture`). Results are kept per way (`TestClip.key`, `asset#DOLBY_VISION`/`#AS_PROFILE_8`/`#BASE_LAYER`; other clips keep their file name) and never become suggested settings: `Profile7Choice` steps a kind down by itself where a way showed no picture and a safer one played (any of its clips, the heavy one counting for FEL): Dolby Vision 7 → converted (where the device can convert) → its base layer (`CapabilityRules.profile7(caps, settings, layers)`, read when each file opens with its remembered kind, `PlaybackSession.layersOf`); a file whose kind isn't known yet goes that way when either kind needed it. How it plays says why. The clips come from `tools/generate-dolby-vision-clips.sh` (`ONLY_PROFILE7=1`): our own test pattern, 1080p enhancement layers (flat for MEL, a picture for FEL), the RPU from dovi_tool's MIT test RPUs (`assets/tests/{mel,fel}_orig.bin`) repeated per frame with the letterbox cleared, muxed with `dovi_tool mux` and `mkvmerge`.
