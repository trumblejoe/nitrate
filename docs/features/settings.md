# Settings, accounts, profiles and backups

Display profiles, how Settings is laid out and searched, first-run setup, device backups, accounts and servers, self-update.

Read CLAUDE.md first: its rules (keys, ids, privacy, licences, focus, server load) apply here too.

- Display profiles (core `pages/DisplayProfiles`): display settings live in profiles; each device's choice of profile is device-only (`DisplaySettingsStore.useProfile`, stored outside the synced map). Profile entries are stored as `p:<profile>:<name>`; shared on every device (`DisplayProfiles.isShared`): custom pages and their layouts (`layout:custom/...`), per-series languages (`tracks`), the profile list and `shared` (spoiler hiding, read over `DisplayPrefs.hideSpoilers`). Built-in profiles TV/Phone/Tablet (`DeviceKind`, chosen by `AppContainer.deviceKind`) are never written: choosing one asks for a name and creates a profile; a change made while on one forks a profile named after the device. Settings saved before profiles migrate to "My settings" (`migrated`). `SettingsSync` keeps everything under display-preferences id `nitrate-display` (older versions still write the single set under `nitrate`, only read once to seed) and merges per entry against the last agreed copy (`DisplayProfiles.merge`) so devices never undo each other. TV: Settings → Display profile, including importing only another profile's radial menu (differences first).
- Settings layout (same groups on both apps): the settings themselves (Picture & sound with an Advanced page for tunneling, DV profile 7, 3D, resolution limit, learned failures, direct play/stream and the format lists; Subtitles; Display with a "What's shown" page; While watching), then Account & servers, Your watching, Tools (tests, speed check, device report, admin pages), About (updates, plugins, licences). TV: `SettingsHubScreen(SettingsSection…)`, `PlaybackSettingsScreen(page = PlaybackPage…)`, `DisplaySettingsScreen(page = DisplayPage…)`; phone: the Settings tab links to `SettingsPageRoute(SettingsPage…)` (`SettingsPageScreen`). Every page or group says where it applies with core `settings/SettingScope` (this device only / display profile, `DisplaySettingsStore.activeProfileName` / all your devices) via each app's `ScopeTag`. Everyday choices stay on the main pages with a one-line "when to use it"; anything only for troubleshooting goes under Advanced. TV Display → Menu: the menu's kind (Overlay, Side rail, Top bar, Dial), then the kind's own line: for the Overlay "Opens with" (Left / Right / Up: the arrow that opens its pop-up at the page's edge; Menu always does; `DisplayPrefs.tvPopupKey`, stored `tvPopupKey`, Left when unsaved), for the rail "Rail side", for the Top bar "Fade in"; then Black menu (`docs/features/tv-ui.md`). Display settings, so per display profile and synced; found in Settings search under "Menu" (pop-up, opens with).
- Settings search (both apps): a search box at the top of Settings (TV `SettingsHubScreen(onFound)`, phone `SettingsScreen` → `openPlace`) finds any setting by its name or the words around it: core `settings/SettingsSearch` (`SettingEntry`: title, `SettingsPlace`, other words, `SettingsOn` TV/phone/both, admin only; `find` needs every typed word to start a word, names first). Keep `entries` in step when a setting is added, renamed or moved; each app maps every `SettingsPlace` to its page.
- First-run setup (both apps; mobile-ui common, so iOS too): one calm full-screen setup in place of separate prompts on a device's first sign-in, core `setup/FirstRunSetup` (`SetupStep` PROFILE (only with several accounts here or PINs in use) → COPY_SETTINGS (the backup offer: differences before applying, or "Start fresh"; skipping answers it as Not now, so nothing is pushed until answered) → SOUND (the speakers question, left out when `Speakers.shouldAsk` says no, e.g. stereo-only outputs; skipping is a day's "later") → MENU (TV only, when `MenuGroups.suggest` has groups: ticks, the resulting menu and More previewed, "Keep it as it is" leaves everything) → DONE (where to change each later); `steps(SetupFacts)`, "Step n of N" from `progress`, `shouldRun`); each step skippable, Back to the one before, "Skip the rest". app-core `backup/FirstRunSetupStore` (`AppContainer.setup`, a device-only flag `first_run_setup_done` in the backup store, never synced or backed up): `onSignedIn` decides before `DeviceBackupManager.onSignedIn` (an account already settled = an existing install, marked done, never shown), `active` while it shows (update offers, `BackupPrompt`, `SpeakersSetupPrompt` and invites wait), `rerun` from Settings → Account "Set up this device again" (also in Settings search, `SettingsPlace.SETUP`; lists every other device's backup), `finish`. TV `ui/setup/FirstRunSetup` (`FirstRunSetupHost` once Home is in the back stack, `SetupSteps`), phone `ui/FirstRunSetup` (`FirstRunSetupHost`, `PhoneSetupSteps`).
- Device backups: each device's own settings (playback + plugins, `core/backup/DeviceSettings`; never PINs/profile choices, scripts have their own backup) are saved by core-android `backup/DeviceBackupManager` (`AppContainer.backups`) to the user's Jellyfin display preferences (`nitrate-device-<deviceId>`, listed in `nitrate-devices`; each device writes only its own) a few seconds after any change, but only once the account is "settled": after first sign-in a device with other backups asks "Set this device up like…" (`offer`; on a device's first sign-in that question is the first-run setup's Copy settings step, `BackupPrompt` covering the rest) and nothing is pushed until it's answered ("Not now" keeps a reinstalled device's old backup as "(earlier)"). Restores always show `DeviceBackups.differences` first and apply only on confirm; hardware results (overrides, learned failures, height limits, 8/10-bit) carry over only from the same model (`DeviceBackups.restored`). Settings → Device backup on both apps; the phone also exports/imports a file.
- Accounts: `SessionStorage` keeps every signed-in server/user (`StoredSession.key` = "serverUrl|userId") and which is current; `MediaServer.switchAccount`/`forgetAccount`/`savedAccounts`. Apps switch through `AppContainer.switchAccount`/`signOut` (they leave SyncPlay and restart the live connection) and route with `shouldPickProfile`. Profile PINs and "ask who's watching" are device-only (`ProfileStore`), never synced. All accounts share one device id (Jellyfin 12.4 keeps each user's token). Servers: every account on a server keeps the same `localUrl`/`vpnUrl`/`remoteUrl` (plus `serverId` and `primary`), set together via `SessionStorage.update` (in place, current unchanged). `JellyfinClient.reconnect()` probes local → VPN → remote → signed-in address (local with a short timeout), only ever for the same server id; `restoreSession` starts on the primary server; `AppContainer` reconnects on network changes (restarting the live connection if the address moved). `serverUrl` stays the address signed in with, so the account key never changes. `MediaServer.servers()`/`saveServerAddresses`/`setPrimaryServer`/`testAddress` back each app's Servers screen.
- Self-update: `core/update/Releases` reads the GitHub releases API (channel from the app id: `.dev` → dev pre-releases, `.debug` → none; version code from the `nitrate-version-code` marker in the notes, else `dev-N` → 1000+N; "What's new" = the notes' list items, written by `release.yml`). `core-android/update/AppUpdater` (`AppContainer.updater`) downloads, verifies against `SHA256SUMS` and installs through `PackageInstaller`; each app shows `UpdatePrompt`. Keep the asset names `nitrate-<mobile|tv>-<name>.apk`. Settings → Updates also shows admins the server's Nitrate Companion (check now; restart the server to finish a waiting update, refused while anything plays), and Settings opens with a "Server update waiting" line while one waits: see `docs/features/companion.md`.
