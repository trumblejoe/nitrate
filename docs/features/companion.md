# Nitrate Companion (server plugin)

What the plugin does and how the apps use it.

Read CLAUDE.md first: its rules (keys, ids, privacy, licences, focus, server load) apply here too.

- `companion/` – Nitrate Companion, a Jellyfin server plugin (C#, .NET 10, against Jellyfin 12.4's NuGet packages; GPL-3.0 because it builds on Jellyfin's libraries) for what Jellyfin has no API for: chat in Group Watch Sessions (and SyncPlay groups from older apps) (`/Nitrate/Chat`, long polling; each message is one timeline note, see Insights below), single sign-on (`/Nitrate/Sso`, open), household channels (`/Nitrate/Channels`), watch groups and private accounts (`/Nitrate/Partners`, `/Nitrate/Privacy`; a group is people plus one or more titles (`WatchGroup.Titles`; groups stored with one `SeriesId` read as a one-title list, `SeriesId`/`SeriesName` still written as the first), each title added or removed by any member (`…/Groups/{id}/Titles`); every group keeps its own watched record per member (`WatchGroup.Watched`; older groups seeded once from each member's own played parts, `RecordKept`), marked per group (`…/Groups/{id}/Mark`, several groups at once with `/Nitrate/Partners/Mark`) and never touching anyone's Jellyfin watched state; a group's schedule carries the Together switch (`Together`, the older "together only", false by default; `SoftLock` kept but ignored) and "If someone plays ahead" (`Locked`: false Ask first, the default and what older groups read as; true Don't allow, kept and voted like the rest of the schedule, enforced only by Nitrate's apps; feature `schedulelock`, without which the apps don't offer it) and each title's view (`TitleView`: `LockedFromId`/`OpensAt` by the schedule, `TogetherFromId` the first part the group hasn't watched); live sessions said to be for a group (`PUT …/Groups/{id}/Session`) count what they play for it; feature `groupwatch`; Group Watch Session times (the older watch party times, `party` in the API) and each night's state, `/Nitrate/Partners/Groups/{id}/Party…`, with reminders and news pushed to members' open Nitrate apps over Jellyfin's session connection by `Partners/PartyPush`, feature `party`; schedule changes go the same way under the same `Nitrate.Party` header as kinds `schedule-ask` (to the members but the asker) and `schedule-done` (to every member, `Outcome` passed/failed/lapsed; `ScheduleMessage`, `PartnerHub.ScheduleAnnounced`, lapses found by `PartnerHub.DueChanges` on the half-minute tick), carrying the party message's fields too so older apps read it as party news that asks nothing: see `docs/features/partners.md`) and shared screenplays (`/Nitrate/Scripts`: owner + invited members, compare-and-set edits on the latest version, long-polled edits and cursors, kept in the plugin's database: `Scripts/DbScriptStorage`, every accepted edit one `script_edits` row, the whole script (`scripts` row) written at most every 30 s while people type and at once otherwise, the edits after the last whole copy replayed on start; `CreditScanner` = the nightly "Find scenes in the credits" task: every film and episodes tagged with a stinger, the end read by the server's ffmpeg (`IMediaEncoder.EncoderPath`) the cheap way (`Credits/CreditReader`): only keyframes decoded (`-skip_frame nokey -skip_loop_filter all -ss <from> [-t <len+1>] -i <file> -an -sn -dn -fps_mode passthrough -vf showinfo,scale=320:180:flags=area,format=yuv420p -f rawvideo -pix_fmt yuv420p -`, one frame per keyframe, typically every 2–5 s and irregular, each at its own time from `showinfo`'s `pts_time`, frames past the asked end cut by their times), backwards from the end in 3-minute chunks (newest first, the newest read to the file's end), stopping once more than `MaxSceneMs` (6 min) of pictures lie before the earliest credits frame read (or before the end, with none) or at 70% (`CreditReader.ShouldStop`: anything earlier would be followed by a longer "scene" than one in the credits can be and is too far back to join the final credits, so it can't change the result; while credits keep appearing, a long roll or a scene in the middle of the credits, the earliest credits frame moves back with them and reading goes on); the first frame of each chunk is measured again against the next-older chunk's last picture (the only pictures kept, one each); measured as the frames stream in, one frame's bytes held at a time and only the features kept, never pictures (`CreditScanJob.ReadFramesAsync`, `CreditRunBuilder`; measuring runs at about 600 frames a second on one core, so decoding is the cost: a 2-hour film with 8 minutes of credits is read back about 15 minutes, a few hundred keyframes plus a few closer looks, instead of every second of its last 36 minutes); in hardware when Jellyfin decodes that file's codec in hardware (`Credits/HardwareDecoding`, from Jellyfin's own Dashboard → Playback → Transcoding settings via `IServerConfigurationManager.GetEncodingOptions()`: the acceleration, its device, the "Enable hardware decoding for" codecs and the 10-bit HEVC/VP9 and HEVC RExt ticks, against the file's video stream from `IMediaSourceManager`, and only when the server's ffmpeg has that `-hwaccel` (`IMediaEncoder.SupportsHwaccel`); Apps find it with `GET /Nitrate/Companion` and hide features without it: asked at sign-in, again when the app comes back into view if not for 10 minutes (`AppContainer.onAppShown`, from both apps' `onStart`), and after a failed ask (no network yet, the server restarting) 30 s, 2 min and 10 min later, keeping what was known meanwhile; a failure at sign-in used to hide every Companion feature (Watch groups in Settings, invites answering from their card) until the app was closed (`CompanionCheckTest`). Two parts (`docs/features/companion-hotswap.md`): the shell Jellyfin loads (`companion/Nitrate.Companion`: `Plugin`, configuration, dashboard page, test clips, and fixed registrations that forward to the logic: one catch-all controller for `/Nitrate/*` enforcing each route's auth, the scheduled tasks under their old type names, the segment provider, request timing, `Hosting/LogicHost`) and the logic (`companion/Nitrate.Companion.Logic`: every controller, hub, store, scanner and rule, in its own service container), loaded into a collectible context and swapped without restarting Jellyfin, its in-memory state handed over. Released as `nitrate-companion-<v>.zip` (the shell, with its built-in logic package) plus a plugin-repository manifest on the `companion-repo` release (`tools/companion-manifest.py`), and, when the logic changed, a signed `nitrate-companion-logic-<v>.zip` listed in `logic.json` beside it (secret `COMPANION_LOGIC_SIGNING_KEY`); the plugin manifest gets a version only when the shell changed. Updates itself: `Updates/SelfUpdater` looks for newer logic (`Updates/LogicUpdater`: signed, swapped in at once, no restart) and asks the server's plugin repositories every 6 hours (first 10 minutes after start) and installs a newer version of itself through `IInstallationManager` unless auto-update is off on its plugin page; with `RestartForUpdates` (off by default, dashboard "Finish updates by restarting at night") it restarts the server (`ISystemManager.Restart`) once a newer copy waits for a restart, in the two hours from `RestartHour` (server time, default 4) and only with nothing playing (`UpdatePolicy`). Admins can also finish it themselves: `/Nitrate/Updates` (feature `updates`, admins only; the shell's `Updates/UpdatesController`) gives where updates stand (`UpdateStatus`: running, waiting, restart needed, sessions playing, last check; and the shell and logic versions, where the logic came from, the last swap, `WaitingKind` and a logic waiting for a newer plugin), `POST …/Check` looks and installs at once (even with auto-update off: the admin asked), and `POST …/Restart` restarts the server only to finish a waiting update and never while anything plays (409 with the reason; `UpdatePolicy.CanRestartNow`). The plugin's dashboard page shows the same: a "Check for updates now" button, and a banner with "Restart now" (asks first; disabled while something plays) when a newer version waits. The apps show it to admins on Settings → Updates ("Nitrate Companion on your server": Check now, Restart now after a question; core `CompanionUpdates`, `MediaServer.companionUpdates/checkCompanionUpdates/restartForCompanionUpdate`, `AppContainer.companionUpdates`, asked once when Settings opens), and a "Server update waiting" line at the top of Settings while one waits. The csproj sets only `<Version>`, so the release's `-p:Version=0.1.0.<run>` stamps the DLL too: Jellyfin compares the running DLL's version with meta.json and the repository's, so never pin `AssemblyVersion`. Its plugin id is a storage key: never change it. Test with `dotnet test companion/Nitrate.Companion.Tests`.

- Library images overview (feature `imagesurvey`; admins, 403 otherwise): `POST /Nitrate/Images/Overview` with `{"LibraryId": id|null, "Expected": {"Movie": ["Primary","Backdrop","Logo"], …}, "Sizes": [{"Type","ItemKind"|null,"MinWidth","Ratio"|null}], "Only": "missing|small|shape|gone"|null, "OnlyType": "Primary"|null, "Limit": 300}` (the rules come from the app, core `admin/ImageGuide`). `ImagesController` reads every film, show, season, episode, collection, music video and video in the library (`GetItemList`, no virtual items) and each image's database record (`ImageInfos`: type, path, width, height, local or only an address; chapter images left out); `Images/ImageSurvey.Run` answers `{"Items","Images","Bytes","Types":[{"Type","Count","Bytes","Small","Misshapen","UnknownSize","NotSaved","Gone"}],"Kinds":[{"Kind","Items","Complete","Bytes","Missing":{"Logo":2}}],"Problems":[{"Id","Name","Kind","SeriesName","Season","Episode","Missing":[…],"Flaws":[{"Type","Index","Width","Height","Flaw":"small|shape|gone"}]}],"ProblemsTotal","Largest":[{"Id","Name","Kind","SeriesName","Season","Episode","Type","Index","Bytes","Width","Height"}]}` (problems sorted by show or name, then season and episode; 20 largest).
