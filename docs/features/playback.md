# Playback

Deciding how things play, tracks, sound (dialogue boost, upmix), refresh rate, Dolby Vision 7, 3D, credits scenes, Up Next, recaps, downloads and the player's Info.

Read CLAUDE.md first: its rules (keys, ids, privacy, licences, focus, server load) apply here too.

- Direct play first, then the device's hardware decoder, its own software decoder, Nitrate's FFmpeg; the server converts only what none of those can do. `PlaybackSettings.maxBitrate` defaults to `NO_LIMIT` (1 Gbps; Jellyfin takes an Int): a file is never converted for its bitrate alone (a slow network buffers instead); "No limit" is the first `BITRATES` choice. Learned failures are narrow: a title that fails as it is (`recordFailure(..., itemId)`) is converted from then on (`failedTitles`, `convertsTitle`, forced in `PlaybackSession.start`; PlaybackDoctor offers `ForgetTitle`), a whole codec/HDR type only once `LearnedFailure.BLOCK_TITLES` (3) different titles failed (`blocksFormat`; older count-only records need a count of 3), and both are let go after `KEEP_MS` (60 days, `forgetOldFailures`). The profile converts up front only profiles no decoder here takes (`VideoCodecCaps.missingProfiles`, from `DeviceProbe.CHECKED_PROFILES`: H.264 4:2:2/4:4:4, HEVC Range Extensions, which Android can't even claim), except that H.264's go to Nitrate's FFmpeg up to 1080p progressive when it's built (`softwareProfiles`; Media3 picks it when MediaCodec turns the profile down); "Always" for a codec lifts this. Those source-dependent rules (software profiles, 10-bit H.264 in software up to 1080p: `CodecProfileDto.applyConditions`) carry `container = "-ts"` (Android/desktop): Jellyfin tests applyConditions against the source when converting too and caps the whole conversion by the smallest size of any profile that matches, so without it a 10-bit 4K HEVC film converted at 1080p. A converted film stays H.264 (tone-mapped to SDR) while the server's "Allow encoding in HEVC format" is off: Server settings shows it. Media3 direct plays AVI, MPEG program streams (.mpg/.vob) and FLV too (`DIRECT_PLAY_CONTAINERS`; the DV profile 7 extractors factory wraps Media3's defaults).
- Playback capability ids are a codec name (`hevc`, `eac3`) or `range:<HDR format>`. Playback settings are per device and must never be synced; display settings are per user and sync through `SettingsSync`. Track choices (`TrackMemoryStore`, keyed by core `TrackSelection.memoryKey`: the show for an episode, the title itself for a movie, kept for good) are display settings and sync, and hold only the kind of track the user picked (audio or subtitles, language plus the track's title so "Commentary"/"Signs" is found again; `TrackMemory.VERSION`) so the rest follows the server account's language settings, which Jellyfin applies through PlaybackInfo's default stream indices. What starts is `TrackSelection.initial`: pick → server's picks → file flags; playback reports carry the audio and subtitle stream indices (sent again at once after a track change), so the dashboard shows them and, with the account's Remember selections on, the server keeps the last pick per title (by index; not across episodes, which is what Nitrate's own memory adds); picks can be made in the player, on details pages (phone `TrackLine`, TV `TrackButtons`, via `AppContainer.trackSetup`/`pickTrack`; How it plays uses them) and in the download dialog (`TrackRequest`; a smaller copy keeps only the picked audio; "Burn-In Subtitles" has the server draw the picked subtitle into a converted download, `DownloadRecord.burnedSubtitle`, listed with delivery ENCODE); night mode, subtitle style, PiP and background audio are playback settings.
- Dolby Vision profile 7 (dual layer, `DOVIWithEL`/`DOVIWithELHDR10Plus`): direct played wherever HDR10 is allowed or it plays as Dolby Vision (`CapabilityRules.allowedRangeTypes`). `CapabilityRules.profile7` picks `Profile7Playback`: as itself (a decoder takes profile 7), `AS_PROFILE_8` (a profile 8 decoder, `DeviceCapabilities.dolbyVisionConverter`, `PlaybackSettings.convertProfile7`, on by default) or `BASE_LAYER`; core-android `DolbyVisionProfile7` (the extractors factory in `PlaybackSession`) gathers each frame, drops the enhancement layer (NAL 63) and rewrites the RPU (NAL 62) with `:dovi-converter` (`RpuConverter`, libdovi mode 2) announced as `dvhe.08`, or announces the HEVC base layer and drops both (`DROP`): a plain HEVC decoder can't use them, so the picture is the same, but MediaTek's showed black with sound when a full enhancement layer reached it (Catching Fire, a FraMeSToR remux). Media3 1.12's own profile 7 → HEVC fallback passes the frames unchanged, so it wouldn't fix that. As Dolby Vision (a decoder takes profile 7) frames pass untouched. Dolby Vision MKVs declare block additions (their dvcC mapping, `MaxBlockAdditionID` 1), so Media3 flags every frame `BUFFER_FLAG_HAS_SUPPLEMENTAL_DATA` and hands it over as [main size][main][extra]: `withSupplemental` rewrites the main part inside that (before, such frames went through untouched in every mode, so no MKV was ever converted or stripped). mobile `DolbyVisionMkvTest` runs the playback test's MKV clips through Media3's own Matroska extractor and checks what reaches the decoder in each mode. The log says how a profile 7 track plays as it opens (`onProfile7`). `DeviceProbe.cached` is the once-per-run probe. Which kind of profile 7 a file is (core `DolbyVisionLayers`: MEL, a minimal enhancement layer, or FEL, a full one) is measured while converting or playing the base layer, from the enhancement layer's average size over the first 48 frames that carry one (`DolbyVisionProfile7(onLayers)`, over 3,000 bytes a frame is FEL), logged in the player's events with its size a frame, shown in Info's HDR line ("FEL, converted to profile 8.1 here") and remembered for the file on this device (`AppContainer.rememberDvLayers`/`dvLayersOf`, the device's key-values) for How it plays ("Dolby Vision profile 7 (FEL) …", else "MEL or FEL: known once played").
- 3D: `MediaItem.video3D` (core `playback/ThreeD`, from `Video3DFormat`); side-by-side/top-and-bottom are shown in 2D unless `PlaybackSettings.threeD` is "As the file is", by `PlaybackSession.applyThreeD` (media3-effect `Crop` + `ScaleAndRotateTransformation`, set only for 3D films and taken off after); MVC plays its 2D base view as is.
- Refresh rate (TV): `PlaybackSettings.frameRateMatch` (Off / Only when seamless / Always), per device; `FrameRateMatcher` switches modes via core `DisplayModes.best`: an exact whole multiple at the same resolution first (23.976 → 23.976 Hz before 47.952/119.88), else a near one within `DisplayModes.NEAR` (24 Hz for 23.976) rather than leave 3:2 judder, never away from a mode that already nearly fits; `DisplayModes.cadence` says EXACT/NEAR/JUDDER. The TV's black while it re-syncs can't be shortened, so the matcher switches before the video starts (the server's stream frame rate, then the file's), holds playback behind `MatchingRefreshRate` until the mode changed plus `SETTLE_MS`, keeps the rate after the player closes as `PlaybackSettings.refreshHold` says (core `RefreshHold`, per device, Picture & sound only, never the player's menu: Always = default, kept while Nitrate is in use, `MainActivity.onStop` → `resetRefreshRate`; 15 minutes; Never = `KEEP_MS`, so the next episode or an extra still switches once; `ModeHold`; the settings page hands the rate back at once when it's no longer wanted), resets at once only when the choice stops being Always (`match` is null until settings load, so a default never hands a kept rate back), and logs what it saw and did. A switch drops the HDMI link for a moment (the output takes only PCM meanwhile), so sound set up then was decoded and stayed so: the track selector re-chooses on capability changes (`setAllowInvalidateSelectionsOnRendererCapabilitiesChange`), and after the settle the matcher calls `PlaybackSession.recheckAudioOutput()`, which rebuilds the audio (audio track type off and on) when surround the output takes again was decoded for no reason of Nitrate's own. The switch is made before the player sets up sound at all: `PlaybackSession.beforePlay` (set by `FrameRateMatcher`) runs once the server answered and before `play`, switching to the stream's rate; after the settle the matcher waits for surround passthrough to come back (`awaitPassthrough`, for as long as this TV's device check measured, else 4 s) before rechecking. Settings → Picture & sound has "How refresh rate works" (`RefreshRateInfo`).
- Dialogue boost: core `playback/DialogueBoost` (surround: centre up, the rest down; stereo: the mid channel's speech band, 1.8 kHz band-pass, added back louder and the sides turned down; limited) runs in core-android `NightModeAudioProcessor` before night mode; one "Sound" choice with night mode, core `playback/SoundMode` (Normal / Clearer dialogue = boost / Night = night mode + boost, stored as `PlaybackSettings.dialogueBoost`/`nightMode` per device; `soundMode`/`withSoundMode`), `PlaybackSession.setSoundMode`/`soundMode`; like night mode it decodes sound that would be passed through (`active`). Player More (Sound chips) and Settings → Picture & sound on both apps.
- Upmix stereo (films and episodes only; `PlaybackSettings.upmixStereo` = "Automatic", on by default, Off = always stereo; per device; the answer to the speakers question is what decides, `SpeakerLayout.KEEP_STEREO`, "Keep Stereo (Use Receiver's Upmixers)", for receivers that upmix themselves): core `playback/Upmixer` (Pro Logic II–style: centre = what L/R share as far as they match, fronts less part of it, surrounds = L−R delayed ~15 ms, softened above 7 kHz, opposite phase; LFE = shared bass < 120 Hz; 7.1 adds a later, softer back pair; 3.1 goes out as 5.1 with silent surrounds; Android channel order) in core-android `UpmixAudioProcessor`, first in the sink chain (before dialogue boost/night mode). The target comes from the speakers on the output in use: `SpeakerLayout` per `SoundOutput.key` (`PlaybackSettings.speakerLayouts`, hardware-like in backups), core `Speakers.upmixTo`/`layout`/`shouldAsk` (stereo-only outputs never asked or upmixed); core-android `SoundOutputs` follows the media output (Android 13+ says, else a ranking) with `AudioDeviceCallback`, so a soundbar or receiver turning off switches at once; `PlaybackSession.soundOutput`, `recheckUpmix` reloads from the same spot when the choice or output changes. Each app: `SpeakersSettings` (Settings → Picture & sound and player More: switch, current output's layout chips, other outputs to forget) and the question (`SpeakersQuestion`/`SpeakersQuestionDialog`): on a device's first sign-in as the first-run setup's Sound step, else at app start as "Your sound" (`SpeakersSetupPrompt` beside `BackupPrompt`, once the backup question is settled, `DeviceBackupManager.settled`, at most once per run, Skip = a day), and for outputs that appear later only a quiet `SpeakersBanner` in the player while stereo plays (phone: "Set up speakers"; TV: never takes focus, points to More/Settings), once a day per output (`PlaybackSettings.speakerAskLater`, `Speakers.askLater`/`LATER_MS`); Info shows the output and "upmixed stereo → 5.1". Jellyfin has no real upmix (its converter only maps channels and re-encodes), so it's done here.
- Sound path in the player's Info (TV `PlaybackInfoPanel`, phone Info dialog): core `playback/AudioPath` (file's codec/channels/rate/bits; decoded here or sent untouched; what goes out, from Media3's `onAudioTrackInitialized`; Android's mixer rate when it differs; processing on) via `PlaybackSession.audioPath`, with a note for receivers (stereo above 48 kHz won't upmix on Denon/Marantz), and for surround a receiver could take untouched (AC-3, E-AC-3, DTS, TrueHD) that was decoded here, "Why decoded" (`AudioPath.decodeReason`: Night/Clearer dialogue on, a speed other than 1×, or Android's `AudioCapabilities` saying the output won't take that encoding, e.g. Fire TV's Surround Sound setting or a TV over ARC; also in the event log). Only night mode/dialogue boost make Nitrate itself decode (`NightModeDecoding`); the upmixer touches stereo PCM only. `MediaStream.sampleRate` comes from Jellyfin's `SampleRate`.
- Picture path in the player's Info (TV `PlaybackInfoPanel` in two columns, picture | sound; phone Info dialog, scrolling): core `playback/VideoPath` (what the decoder gets incl. HDR as announced, the file's range when it differs, profile 7 handling, software/tunneled decoding, what the server converts to from the stream URL's `VideoCodec`/`MaxHeight`/`VideoBitrate`, the display's mode and HDR kinds via core-android `DisplayInfo`, dropped frames, seconds buffered, network vs. the file's bitrate, how subtitles are drawn and the second one) from `PlaybackSession.videoPath()` (refreshed each second while shown), with notes for judder (`cadenceFits`, 0.05%), dropped frames and a slow network.
- Sound and picture out of step: in the player core `playback/SyncWatch` (fed by `PlaybackSession` from Media3's analytics: `onAudioUnderrun`, `onVideoFrameProcessingOffset`, `onAudioSinkError`, unasked position jumps within an item; the first `SETTLE_MS` after starting or seeking ignored) gives a `SyncWarning` (`SyncTrouble`: sound kept running dry (3 in a minute), picture behind the sound (frames ≥ 40 ms late three batches running), sound restarted, the file's timing jumped), exposed as `PlaybackSession.syncWarning`, logged, shown as a note in the player's Info (`VideoPath.syncTrouble`) and its Path (`Smoothness.syncTrouble`, "Sound and picture"), and first in `diagnosis` with fixes `PlaybackFix.Resync` (reload from here the same way) and `PlaybackFix.Convert` (the server converts from here, this playback only); each player shows "Out of step? Fix it" while there's a warning, even when it plays as it is. Files made out of step are found by the Companion's timing check and listed in Library health as `HealthCheck.TIMING` (`MediaServer.fileTimingIssues`, core `diagnostics/FileTiming`). A constant offset from the TV, receiver or Bluetooth can't be seen by the app; the player's audio-sync setting is for that.
- Drifting sound (sound and picture creeping apart while playing smoothly, fixed by stopping and playing again; typically DTS or Dolby passed through to a receiver, whose timing the device reads poorly): `SyncWatch.clock` is fed every `CLOCK_EVERY_MS` (2 s) by `PlaybackSession` with the player's position against real time while playing steadily (normal speed, ready, not a recap clip or watch-together). Played smoothly the two advance together; a gap growing past `DRIFT_MS` (120 ms) faster than clocks differ by nature (`DRIFT_RATE`, 0.02%), three looks in a row, is drift. A pause or buffering keeps what was measured; a seek, a start or the sound running dry starts afresh. With `PlaybackSettings.autoResync` ("Line up drifting sound", Picture & sound, on by default, per device) the player seeks to where it is, which sets the sound output up afresh (at most once per `FIX_EVERY_MS`, 2 min); after `DRIFTS_FOR_WARNING` (2) re-syncs in one playback the out-of-step warning says so, naming what goes out untouched, and "How it plays" offers "Decode DTS on this device" (`SettingsChange.DecodeHere`, `PlaybackSettings.decodeHere`: the audio sink reports those formats unsupported for passthrough when the device or FFmpeg can decode them, as Night mode does); each such format shows in Picture & sound with "Pass through again". Tunneled playback leaves the syncing to the TV's hardware, so drift there may not show.
- Up Next: episodes roll on (countdown); after a film in a collection, `MediaServer.nextInCollection` (`Items/{id}/Collections`, core `playback/NextInCollection`: the smallest films-only collection of 2–40, release order) is offered at the credits (`NextInCollection.offerAtMs`) with no countdown and never auto-plays. Phone `UpNextCard(seconds = null)`, TV `ui/player/UpNextCard` (Up Next for episodes too; next goes through the playback gate); not in queues or recap clips.
- Scenes in the credits: core `playback/CreditScenes` says whether a title has one (TMDb keywords `aftercreditsstinger`/`duringcreditsstinger`, which Jellyfin keeps as tags) and where: OUTRO segments ending well before the end, else chapter names (a scene chapter after a credits one), else, for films or tagged titles with no marker, what the server found (`MediaServer.serverCreditScenes`, Companion feature `credits`; empty = checked, none, so the device doesn't look again; certainty as for thumbnails), else the scrub thumbnails of the last 30% (core-android `CreditFrames` reads each tile whole, at most 320 across, into brightness and colour and measures it at once, keeping only the features; ≥60 s of credits then ≥15 s of picture; see "How credits are read" below). `CreditCertainty`: MARKED and CONFIRMED (thumbnails + matching tag) skip by themselves, GUESSED is only offered; tags alone give a heads-up. `PlaybackSession.creditScenes`; each app's player runs `CreditSkipper` (acts once per credits stretch, only within 5 s of its start) and shows `CreditSceneBanner` ("Watch credits" undo / "Skip to it" / "Stay for…"); never auto-skips in a SyncPlay group or recap clip; Up Next and Next in collection wait via `CreditScenesInfo.upNextAt`. `DisplayPrefs.creditScenes` (per user, on by default; off = offer only). Read from pictures (the thumbnails here or the Companion's frames), a dark stretch only counts as credits when what follows is short (`MAX_SCENE_MS`, 6 min; the Companion's `CreditFinder.MaxSceneMs`) and the scene starts within `SCENE_NEAR_END_MS` (20 min) of the end, checked on the server's kept results too: a night or smoke-filled scene with the film going on (Batman Begins' escape from the burning house) is not a scene in the credits.
- How credits are read (one definition in core `playback/CreditScenes.kt` (`CreditFeatureReader`, `CreditScenes.verdict`/`verdicts`) and the Companion's `Credits/CreditFeatures.cs` + `CreditFinder.cs`: keep them in step, thresholds are named constants on both sides). The Companion reads the end at 320×180 yuv420p, one frame per keyframe (every 2–5 s, irregular; only keyframes decoded, in hardware when Jellyfin decodes that codec in hardware), backwards from the end in 3-minute chunks until more than 6 minutes of pictures lie before the earliest credits read (or 70% is reached), then decodes about ±1 s around the keyframes either side of each boundary found at 4 frames a second so credits and scene starts land within about a second (`CreditReader`; companion.md has the ffmpeg arguments); readings kept from before were one frame a second over the whole last 30%, and still read the same. Every length (credits ≥ 60 s, scene 15 s–6 min, gaps, final credits, the dialogue's spread) is in milliseconds from each frame's own time, never a count of frames; a frame stands for the time until the next. The apps read their thumbnails (Jellyfin's are 320 wide, 10 s apart). Per frame: shares dark (< 40), bright (> 170) and between; marks (> 110: text, even thin strokes softened by scaling); entropy of the 32-bin brightness histogram (bits); edge sharpness (of neighbouring pairs where a mark meets a non-mark, the share differing by ≥ 80: text is crisp, glow and fire soft); text lines (row projection of marks: bands of rows with ≥ max(2, w/100) marks separated by empty rows, at most 12% of the height tall; the share of marks inside them, `lineInk`; the heights' regularity, 1 − coefficient of variation; symmetry, how centred each line's ends are); strokes (share of runs of marks ≤ 8 px wide at 320, and their mean width); colour (mean max(|U−128|,|V−128|) of the marks: white ≈ 0, orange flame 60+; thumbnails from RGB via BT.601); and against the frame before: the best upward shift of the row means (up to 25% of the height a second apart and for the server's closer looks, 75% between the server's keyframes and for thumbnails 10 s apart, overlap ≥ a quarter), kept as a scroll when the shifted picture differs by ≤ 4 on average and the unshifted by at least twice that plus one, and "still" when unshifted differs by ≤ 1.5. Verdict: not mostly black (dark > 0.72, bright < 0.22, between < 0.18) → picture `.`; ≥ 97% dark with next to no marks → black `b`; marks' colour > 40 → `o`; entropy > 3 bits → `e`; text (sharp ≥ 0.5, strokes ≥ 0.75, ≥ 1 line, lineInk ≥ 0.6) with two regular lines (≥ 0.5) or centred (symmetry ≥ 0.85), or text that is still or scrolling → `C`; a scroll whose neighbour scrolled about as fast (rows a second, as frames are irregular: within 2 rows over the shorter of the two gaps, or 25%; one a second that's max(2, 25%)) → `S`; text moving otherwise `w`. Then: black right after credits counts (`B`: between cards, or to the end), gaps ≤ 3 s between credits frames count (`g`, a fade between cards), and so does a single frame up to 6 s long between them (one keyframe on a fade; none for thumbnails 10 s apart), and a stretch less than half `C`/`S` (by time) is not credits (`f`). Runs, `MIN_CREDITS_MS`, `MIN_SCENE_MS`, the 6- and 20-minute rules apply to what counts. The thumbnails' scroll test is weaker (10 s apart, so only a slow roll overlaps enough; a fast one reads as cards or text and still counts frame by frame), and so is the server's between keyframes (2–5 s apart: a roll faster than about 135 rows over the gap doesn't overlap enough, false matches between similar cards are likelier with the wider search, and the speed check has fewer, irregular neighbours); rolling text still counts as text, and the closer looks at the boundaries are at 4 frames a second. The server adds a dialogue vote from the title's subtitles (Companion `companion.md`); a skip it heard dialogue in (`CreditSkip.spoken`) is CONFIRMED like a matching tag. Tests: core `CreditScenesTest`, the Companion's `CreditTests` (synthetic rolling and card credits, a smoke-filled scene with soft glows, a fire, dialogue) and `CreditReadingTests` (the same at irregular keyframes, reading back stopping early, a scene in the middle of long credits, boundaries within a second despite 10-s GOPs, hardware arguments and the fallback, the file-reading gate).
- "Still watching?": core `playback/StillWatching` (`AppContainer.stillWatching`, lives across players): players report `started` (a roll-on after `rollingOn`, else a press) and `input` (any touch/key, throttled); before an episode rolls on by itself (end or Up Next's countdown, `UpNextCard.onCountdownEnd`) `shouldAsk` (2 roll-ons in a row or 90 min untouched) shows each app's prompt (Keep watching / Go back / Stop); no answer in 5 min or Go back runs `AppContainer.stillWatchingRewind`: resume point 30 s before the last press (`saveUserData`), the episodes that rolled on unwatched (unless seen before). `PlaybackSettings.askStillWatching` (per device, on).
- Dual subtitles: core `playback/SecondSubtitles` (text tracks only; `parse` SRT/WebVTT into `Cue`s, `at`); `PlaybackSession.setSecondSubtitle`/`secondSubtitle` fetches the stream as SRT from the server (or a download's own SRT/VTT) and remembers the language per show for the app run; each app's `SecondSubtitleLine` draws it at the top; picked in player More ("Second subtitles").
- Audio description: `DisplayPrefs.describedAudio` (per user, synced). Jellyfin has no flag and Media3 reads none from MKV/MP4, so core `playback/AudioDescription` recognises described tracks by name; `apply` moves the starting audio to a same-language described track (on) or away from one (off) unless a track was picked for the show (`TrackSelection.initial`, `PlaybackSession.start`/`loadLocal` via `AppContainer.prefersDescribedAudio`, downloads).
- "Last time" recaps: core `recap/Recaps` builds a `Recap` before resuming a show's episode (or the next item of a playlist marked in story order, `DisplayPrefs.recapPlaylists`, shared on every device via `SharedPrefs`) when the last watch (`UserState.lastPlayedMs`) is at least `DisplayPrefs.recapAfterDays` ago for shows, `playlistRecapAfterDays` for playlists (0 = never; per display profile): the last few things watched (never anything ahead), where the user is, and a `RecapClip` of the last one's ending before its credits (server OUTRO segment, else a credits-named chapter, else runtime − 1 min; 3 min). `AppContainer.recapBefore` (2.5 s cap, so playing never waits long) sets `pendingRecap`; each app's play path (phone `go` in `MobileApp`, TV `rememberPlaybackGate`) opens `RecapRoute` instead of the player when one is due; marked playlists get "Continue" on their page. Clips play with `PlaybackSession.loadClip` (`PlayerRoute.clipEndMs`): nothing reported to the server (watch history and resume points untouched), no Up Next, never joined to a SyncPlay group, ends at the clip's end.
- Picture-in-picture: phone (`PictureInPicture`, auto-enter on Android 12+) and TV (`player/TvPictureInPicture` `rememberTvPictureInPicture`: Home while a video plays keeps it in a corner window, auto-enter on 12+, by hand before; the player shows only the picture there; not for recap clips), both `PlaybackSettings.pictureInPicture` (TV: Settings → While watching → "This TV"); the TV player pauses on `ON_STOP` (out of sight, or the small window closed). Sleep timers for video: phone and TV player More (minutes or "End of this"), iOS `IosPlayerMore` the same (`ApplePlayerSession.pause`).
- Theme music: `MediaServer.themeSongs` (`Items/{id}/ThemeSongs`, inheriting the series') and `audioStreamUrl`; core-android `playback/ThemeMusic` (`AppContainer.themeMusic`) plays quietly with fades, keeps one song across details pages (series → season → episode), stops on leaving them, when a player opens and when the app goes to the background (each `MainActivity` onStart/onStop). `DisplayPrefs.themeMusic` (null = device default: on for TV, off for phones); each nav host's `DetailsRoute` show/hide it.
- Downloads: logic in `core/downloads` (`DownloadManager`, common Kotlin with kotlinx-io); Android runs it through WorkManager (`core-android/downloads`), UI in `:mobile` only. A downloaded item plays from the device (`PlayerRoute(local = true)`) and its watch state is recorded locally and sent by `syncWatchState`, never through `/Sessions` reporting. Transcoded downloads need a fresh `playSessionId` each time or the server reuses an old transcode, and arrive as fragmented MP4 with no length or index (unseekable in Media3): core `downloads/Mp4Index` writes a `sidx` after downloading (shifting the fragments' absolute `tfhd` offsets, dropping `mfra`), and `DownloadManager.makeSeekable` repairs older downloads before they play. Jellyfin 12.4 rejects `api_key` query auth: always send the Authorization header.
- Who a playback counts with: the player's group button (watch group, Group Watch Session, same room, just me) and its panel, `docs/features/partners.md`.
- Group chat in the player (Companion `notes`): the watch group's conversation on the title (Companion `threads`: one per group and title) pops up as playback reaches each message, never ahead; on or off by one setting, Settings → Group chat (a display preference, not a playback setting; on by default, off in easy mode), changed for one playback by the player's Turn off/Turn on or the details page's Chat choice (which can also replay an older thread). Details in `docs/features/partners.md`.
- Windows (desktop): mpv plays the file as it is (core `playback/DesktopPlayback`: every codec, container, HDR kind and subtitle; bitstreaming per codec, off by default), Nitrate's own controls and the shared overlays over it; see `docs/features/windows.md`.
