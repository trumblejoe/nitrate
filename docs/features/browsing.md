# Browsing, details, search and server load

Library browsing, details pages, search, lists and playlists, live TV, and how pages load without loading the server.

Read CLAUDE.md first: its rules (keys, ids, privacy, licences, focus, server load) apply here too.

- Images: both apps' Coil loader keeps a 512 MB disk cache; cards ask for small art (`backdropUrl(item, maxWidth)`), only full-screen views take 1920px, and the full-screen Home preloads the pictures one press away. Row pages prefetch into the disk cache (each app's `ImagePrefetch`): `PrefetchAlongRow` for the next cards in a row, `PrefetchRows` for the first cards of the rows below; prefetch the exact address the card uses (`rowCardImage(s)`), so a new row style or image size must update those too.
- Pages reload on server pushes: pass `AppContainer.serverChanges` to `RowsViewModel`. Screens open with what they showed last time from `AppContainer.dataCache` (app-core `DataCache`, in the cache folder: one folder per account, files named by SHA-256 of the key, the least recently written dropped past `MAX_BYTES` (50 MB), the account's folder deleted on sign-out or forgetting it, with the client's remembered library list and "Because you watched" (`TextCache.remove`)) while fresh data loads: page rows (`RowsViewModel`), details pages and each season's episodes (`DetailsViewModel`), the Add-to lists; never wait on it and always replace it with fresh data; Home and library pages load progressively: `MediaServer.homeRowsProgress`/`libraryRowsProgress` run each row (or source of rows) as a core `rows/RowJob` through `ProgressiveRows.run`, emitting the rows so far in page order as each answers, but `RowsViewModel(loadProgress = …)` doesn't show rows one by one (the page would keep jumping): core `rows/PageReveal` swaps the whole page in once complete, or once at the patience mark (1.5 s with nothing shown; 3 s over last time's page, then only replacing rows in place, never adding or moving any), and the rest at the end; row lists use `animateItem` so reload changes slide rather than jump; OkHttp allows 16 requests per server, so keep new rows independent jobs. A job that can show something early uses `RowJob.showing` (Home's "Latest in…" rows show from the library list saved last time, `lastViews`, then follow the fresh `UserViews`, which some servers take seconds to answer). Nothing network-bound should be awaited before Home appears (`onSignedIn` only launches).
- "Because you watched" is kept light for the server: its seeds come from `lastWatchedSeeds` (8 titles, no total count, no pictures), the costly "similar" search is asked for two seeds at a time and for more only when a row came up short (`BecauseYouWatched.rows`), and the rows are kept on the device a day (`BECAUSE_TTL_MS`), their cards' watched marks read afresh each time they're shown from there (`withFreshUserData`: one `Items?ids` request, no pictures); hiding both rows stops it altogether. Other pages can show it as an app row (`AppRows`), sharing Home's answer; and things that read Home's rows in the background use `MediaServer.watchingRows(latest)` (Continue Watching, Next Up and, when asked, each "Latest in…": the TV screensaver and home-screen channels, the phone widgets), never the whole page. Coming back to a details page (`DetailsViewModel.refresh`, on resume and after a change) asks only for the title and one light `MediaServer.userStates` (`Items?ids`, no pictures or counts) for its rows' marks; the full load runs once on opening. Details pages ask for similar titles only while "More like this" shows (`DetailsViewModel(wantsSimilar)` from `DisplayPrefs.similar`).
- Custom rows (a query, collection, playlist or app row added to any page) are kept too while nothing they depend on has changed (`RowChanges.dependsOn(RowSource)`: a query on titles and watch state, a collection on titles, a playlist on playlists and titles, an app row as that row); each is saved with the counters it was read under and its source (`CachedPage.customStamps`, `RowChanges.stampOf`/`keepCustom`), the counters asked once and reused for a few seconds; kept ones get their watched marks read afresh when watch state changed; one custom-row load runs at a time per page. A playlist row reads only its first 24 titles (`MediaServer.playlistRow`, more as it scrolls through `moreOfPlaylist`), never the whole playlist. With the Companion, "Because you watched" is made in the app from the plugin's overnight facts (`/Nitrate/Because/Facts`: what was played lately and the server's similar titles for the films and shows of it) by core `BecauseYouWatched.rows`, each seed's titles read as cards with today's watch state (`cardsFor`); the plugin applies no rule.
- Hidden rows are off, not just out of sight: `RowsViewModel(loadProgressSkipping)` passes the saved layout's hidden built-in keys to `MediaServer.homeRowsProgress(skip)`/`libraryRowsProgress(library, skip)` (and `LibraryTabs.rows(skip)` for Genres/Studios/Decades), whose jobs carry the one row key they make (`RowJob.key`) so a hidden one never runs (Home's "Latest in…" per library too; a job making several fixed rows, `RowJob.making(name, keys)`, runs unless all are hidden: "Because you watched", `BecauseYouWatched.slots()`); `RowsProgress.skipped` gives their titles to the editor; hidden custom rows aren't queried either; showing one again reloads the page. Continue Watching and Next Up as one row (`DisplayPrefs.combineContinueNextUp`, off by default, What's shown on both apps): core `rows/ContinueAndNext` (`KEY` `home/continue_and_next`: part way first, then next episodes of shows not already in it), built by `homeRowsProgress(skip, combineContinueNextUp)` via app-core `homeRowsLoader`; the two separate rows keep their keys (widgets, TV channels and the screensaver use `homeRows()`, which still makes them); each Home reloads when the choice changes.
- Continue Watching leaves out what's half-watched with a watch group while Watching together shows it (that part resumes from the group's card, at the group's own resume point; with the row hidden it stays as the group's card): `WatchPartners.continueWatching` in `homeJobList`, see partners.md. Watching together is on by default and shows the start card alone when nothing's shared.
- App rows on any page: core `rows/AppRows` (Continue Watching, Next Up (both narrowable to a library), Continue Watching and Next Up, Latest in a library, Because you watched 1/2, Continue Listening, Continue Reading (both skipped without a book or mixed library, `mayHoldBooks`), Watching together; keys are stored, never rename) as `RowSource.AppRow(key, libraryId)` custom entries ("App row" in both apps' row builders), loaded by `RowsViewModel.loadCustom` through `MediaServer.appRow`, which makes the same requests as Home's jobs so the shared answers serve both pages.
- More from pages (studio, year, person; `PersonScreen`): one `RowsPage` row (key `more-from/titles`, its look kept for them all, Fast-forward/Rewind or held OK to change it) inside `ThemedPage(PageKeys.MORE_FROM)`; held OK opens the Customize panel like any page (a `RowsViewModel` for `MORE_FROM` that only saves looks, provided as `LocalPageRows`; no Rows item, and no move/rename/hide, since there's one row; theme, background and Layout as other pages).
- Details pages (both apps; films, episodes, shows and seasons, a season being its show's page opened at it): an episode names where it belongs first ("Show › Season", each opening its page: TV `WhereItBelongs` crumbs, phone the same in the hero), then its own name. One short action row: Play/Resume, From start, Trailer, then Watched, Favorite and More (TV round `RoundAction`s whose name shows under the row while focused; the phone's row adds Download and Play on…); What Play starts with is one quiet line (TV `StartsWithLine`: audio, subtitles, version, one dialog; the phone's `TrackLine`/`VersionChooser`). Everything else is under More (TV `MorePanel`, phone `DetailsMoreSheet`): How it plays, Moments, Earlier chat, Add to a playlist or collection, More from studio/year, Manage, Comic details; new page actions go there, not on the row. A season's page (the show's page opened with `seasonId`) is headed by the season: "Show › Season 2" (the show opening its own page), the season's name, "10 episodes · 6 watched", the season's own description (else the show's), and Play for that season's next unwatched episode, else its first; the chips switching season update it. The action row's pieces are shared (`components/Actions.kt`: `RoundAction`, `ActionHint`, `Crumb`, `ShuffleIcon`), and the TV video playlist page uses them too (Continue or Play primary, Play from the start, round Shuffle and More holding Edit, In story order, Rename, Delete). Pages on their way show placeholders in their own shape, never a bare "Loading…" (`components/Placeholders.kt`: `DetailsPlaceholder`, `RowsPlaceholder`, `ListPlaceholder`, `GridPlaceholder`, a soft pulse, read out as "Loading"); a failure still shows its message. Below: an episode's page shows its season's episodes (the show's season chips too, `DetailsViewModel` loads them for an episode; "This one" marked, focus entering the row lands on it, selecting it plays), a film's page its collection (`DetailsState.collection`, `NextInCollection.saga`, "The collection"), then cast, extras, More like this.
- Home without asking twice (with the Companion; each falls back to the requests before): Continue Reading and Listening come in the Home bundle (`reading`/`listening`, kept under the rows' own request keys), and an empty one asked alone is taken as empty for 10 minutes unless watch state changes (`quietRows`); "Continue your playlists" asks the Companion for facts (`MediaServer.playlistFacts`, `/Nitrate/Playlists/Watching`, since the start of the day 60 days ago) and applies the app's own rules to them (`PlaylistPlaying.fromFacts`: core `PlaylistPlaces.entries`/`lastPlayed`/`continueFrom`, the same for the player's next-in-playlist), then reads the chosen cards in one request (`cardsFor`); when the Companion offers them but doesn't answer, nothing is read here instead: the row keeps its last answer (memory, then the device, `playlist-row`) with watched marks read afresh, it isn't asked again for a minute (`RETRY_MS`), and the query analyzer shows "Continue your playlists: … hasn't answered since …" (`PlaylistPlaying.status`, also in what Copy copies); without the Companion each playlist's members are kept on the device until its etag changes (`playlists()` asks `Etag`, `MediaItem.version`; `PlaylistPlaying.membersOf`); the library list kept on the device is used without asking for 30 minutes (`VIEWS_KEEP_MS`, `viewsRecent`) unless a library change is heard. Pages keep rows nothing changed for: `RowsViewModel` asks `MediaServer.changeCheck(stamps)` (`/Nitrate/Changes`, never kept) when a page opens or the server says something changed, keeps the rows whose contents depend only on unchanged areas (core `rows/RowChanges.dependsOn`: "Latest in…" on titles and libraries; Continue Watching, Next Up, Reading, Listening on titles and watch state; Continue your playlists also on playlists; Because you watched also on its nightly build; a library's rows on titles and watch state; anything else, the watch groups' row included, always loads), reads only their watched marks afresh when watch state changed (`withFreshMarks`), passes them to the loader as skipped and merges them back in the page's order (`RowChanges.merge`); the counters are saved with the page (`CachedPage.stamps`). Pull to refresh and setting changes load everything.
- Search: screens show `MediaServer.searchHints` (`Search/Hints`, cheap) first, then `search` replaces it. Search finds films, shows, episodes, collections and playlists (one request), people (from the hints), and from the areas the user has libraries for (core `search/SearchScope.areas` over the library list kept on the device, `AppContainer.searchAreas`; never asked of a server without them) music artists and albums, audiobooks and books, music and home videos, and Live TV channels (`SearchArea`; one more request) and songs (a request of their own, so a common word's many songs don't push out albums; `SearchResults.songsByArtist` groups them by the album's artist, then album, in disc and track order). The phone (mobile-ui `SearchScreen`, so iOS and the desktop too) shows them in sections after Collections, songs under "Artist · Album" headings (tap the heading for the album); the TV shows a row per kind and a row of songs per artist and album. A song or a channel plays at once (phone `playOrOpen`, TV `onPlay` through `PlaybackGate`); everything else opens its page (playlists their playlist page). Programmes in the guide aren't searched. Packing for a trip's "Add…" uses the same search (playlists and videos too; no music or channels). Recent searches (app-core `SearchHistoryStore`, 12 at most) belong to the account (`recent/<account key>`), so switching accounts shows each its own; signing out or forgetting an account removes its list, and the old device-wide list from before is dropped unshown. Versions: `MediaItem.versions` from the item's media sources; `resolvePlayback` with no `mediaSourceId` picks the source this device direct-plays, then direct-streams, then the first; a choice on the details page lives in core-android `VersionChoices` (in memory) and `PlaybackSession` uses it. Multi-part titles (`partCount`) play on through `additionalParts` inside `PlaybackSession`. Details: `extras` (local trailers + special features) as an Extras row and a Trailer button (remote trailers open the URL), "More from <studio>/<year>" via `PersonRoute(studio=, year=)` and core `Browse.byStudio`/`byYear`. Players: chapter list (`chapterImageUrl`, core `playback/Chapters`), TV media next/previous jump chapters. There is no Upcoming row (removed: new episodes reach Next Up anyway). `MediaItem.isMissing` (virtual episodes) is never playable and labelled by core `AirDates.status`; whether seasons include them is the server account's `DisplayMissingEpisodes` (`showsMissingEpisodes`/`setShowMissingEpisodes`, round-tripping `Users/Me` Configuration). Browse filter choices come from `libraryFilters` (`Items/Filters`): genres, decades from real years, age ratings, tags.
- Filters' tags: a library can have hundreds, so the filter panel (TV `FilterDialog`, phone `FilterSheet`; Clear all at the top beside Done on both) shows only the chosen tags (each removable) and "Choose tags… (n)" / "More tags…", which opens a panel of their own (TV `TagPanel`, phone `TagSheet`): typing finds tags (core `pages/TagChoices.matches`: names starting with what's typed, then a word in them, then any part; TV ▼ from the box goes to the first match), or they're paged 24 at a time most used first (`TagChoices.rank`: the chosen ones, then by count, then A–Z), the counts from one request when the panel opens (`MediaServer.tagCounts`: the tags of up to 1,000 of the library's titles). TV tabs bar: the library's tabs keep their whole width (sliding sideways when there are more than fit) and Sort/Filters/Clear go on a line of their own below when they don't fit beside them (`TabsAndButtons`), never squeezing a tab onto two lines.

It is the page's, not the view's: TV `BrowseLibrary` `JumpColumn`/`JumpRow` placed by `tvLetterBar` (right by default; left, top), 22 dp for letters, wider for word stops, the stop of the chosen title lit; the phone's `JumpStrip` down the right of every view (drag or tap). - Lists: playlists and collections are edited through `MediaServer` (`createPlaylist`, `addToPlaylist`, `movePlaylistItem`... by `MediaItem.playlistEntryId`; `createCollection`... needs `AccountInfo.canManageCollections`). Each app has an `AddToListDialog`: multi-select over both lists at once (TV: two columns; phone: tabs), new lists only created on confirm, always a review step before anything is added; logic in core `lists/AddToLists` (`load` fetches both together, `apply` reports each target).
- Playlists played in order (both apps): a video playlist's order is the watch order the user curated (often with a plugin that builds such playlists), so it plays as itself. core `playlists/PlaylistPlaces` (`candidates` leaves out music playlists; `entries`: shows and seasons put in whole become their episodes, specials and missing ones left out; `progress` = `PlaylistStatus` watched/total/next; `nextUp`) and app-core `playlists/PlaylistPlaying` (`AppContainer.playlists`: each playlist's entries a minute in memory and on disk in `DataCache`, so a big one opens at once). Kept light, since Home asks on every reload: which playlists are being watched comes from one small `MediaServer.recentlyPlayed` (newest plays, no pictures or counts) checked against each playlist's ids (`playlistMembers`: no pictures, user data or fields; kept `STRUCTURE_MS`, 6 h; the playlist list `LIST_MS`, 30 min, let go at once when this app changes a playlist: `MediaServer.onPlaylistsChanged` → `playlistsChanged`; without any video playlists nothing more is asked); only those matching have their whole contents read (shows in whole as their episodes; kept `STRUCTURE_MS` in memory and on disk), with watch state laid over them from the played-lately answer (`PlaylistPlayingTest` counts the requests: after the first visit, one per Home reload). Where each playlist was left comes from Jellyfin, not Nitrate: the entry played most recently (`PlaylistPlaces.lastPlayed`, each item's `UserState.lastPlayedMs`), so watching in any app on any device counts and nothing is stored or synced; a playlist is being watched through when something in it was played within `ACTIVE_MS` (60 days). The one thing kept, in memory for the run, is which playlist a title was just started from (`startedFrom`, before the server has a play date for it; rolling on adds the next one). Every player asks `contextOf(item)` when a title starts: the playlist it was just started from, else among the user's video playlists (`LOOK_IN`, 20; kept copies first) one watched lately whose last-played entry is this item, the one before it (gone back), or up to `PLACE_AHEAD` past it (past any watched since; `indexNearPlace`; a whole show or season started from the page means its first unwatched episode, `placeIndex`); then Up Next is the playlist's next entry, rolling on whatever it is (`inPlaylist`: a film counts down like an episode), so resuming from Continue Watching or Home carries on in the playlist's order too. Home's "Continue your playlists" (key `home/continue_playlists`, `continueRow`: per playlist watched lately, `continueFrom` its last-played entry, most recent first; added by app-core `homeRowsLoader(…, playlists)` after Next Up via `HomePlaylistsRow.insert`, made side by side and never holding the page up; on by default, hideable like any row). The playlist page (TV `playlist/PlaylistScreen`, phone `PlaylistScreen` in `LibraryScreens.kt`; always the large header, no view switch) is the one place for it: how much is watched (bar and "12 of 40 watched"), Continue from where it was left, Play from the start, Shuffle, the entry you're up to marked NEXT (a whole show's entry when its episode is next), watched marks; holding OK (TV; also its Edit entry panel) or a long press or the entry's ⋮ (phone) on a video entry offers Play from here, Open it, Mark watched up to here and Mark unwatched from here on (`markUpTo`, a whole show or season counting as all its episodes); Edit keeps move/remove/rename/delete; music playlists play as queues (Play all/Shuffle); "In story order" (recaps) as before. There are no franchise hubs, no Franchises menu stop (an old saved arrangement holding `franchises` just drops it) and no alternative watch orders. Mood scenes in TV `effects/Realism5.kt` (any page can use them): Lightning run, Night watch, Cosmic rift, Arena at dusk, High kingdom, Spellbound (skylines with rim light and lit windows, volumetric `beam`s, `embers`, `ridge`s with haze; original drawings, moods only). `SceneGalleryTest` draws themes to `tv/build/outputs/scenes` with `-Pscenes=NAME,…` (and `-PsceneTimes=`) for looking at while drawing.
- Playlists keep their own record (core `playlists/PlaylistRecord`, `PlaylistRecords`; app-core `playlists/PlaylistRecordStore`: on the server when the Companion keeps them (feature `playlistrecords`, `MediaServer.playlistRecords/playlistRecord/putPlaylistRecord`; records kept in settings before are moved up once per account and device, none replacing one kept there), else with the user's synced settings, one shared entry per playlist: `DisplayProfiles.PLAYLIST_RECORD` "plrec:<playlist id>", never rename): which of its entries were watched in it, each one's resume point, and the last one played from it. Watching a title on its own never touches a playlist's record, and a playlist sitting never touches the user's own Watched mark or resume point: `PlaylistPlaying.entries` lays the record over the entries (`PlaylistRecords.apply`), so every rule in `PlaylistPlaces` (progress, NEXT, carrying on) reads the playlist's own progress. A record starts once from the user's own marks (`PlaylistRecords.seed`; the playlists being watched by them are seeded the first time "Continue your playlists" loads, `seedOnce`, once per account and device; any other the first time it's opened), then the two stay apart. A play is a playlist sitting only when it was started from a playlist: its page (Play from here, Continue, a title in it, a queue played through from it), a "Continue your playlists" card, a title opened from the playlist (`DetailsRoute.playlist` on both apps; phone `AppActions.fromPlaylist`), or the next one rolling on in it; such items carry `MediaItem.playlistId`, and `AppContainer.playStartMs` (both apps' play path, with watch groups' resume points) marks the sitting (`PlaylistPlaying.startedFrom`) and starts it at the playlist's own resume point; any play without the tag is the user's own (`playsOnItsOwn`), whatever was started before. Nothing is guessed from what was played lately (the old "a playlist whose last-played entry this is" rule made Up Next jump to another show when an episode from Continue Watching was also in a playlist). The player asks `PlaylistPlaying.contextOf` for every playback (queues too): for a sitting it registers the user's own state (`MediaServer.keepOwnState(item, playlist, before)`: with the Companion, `POST /Nitrate/Playlists/Sitting`, and the server moves the record on and puts their state back (play count too) when Jellyfin says it stopped, even if the app was closed meanwhile; the app's stop waits for the state coming back, as for group plays, and `PlayStop.recordedByServer` has `followStops` read the record rather than work it out; without the Companion, `JellyfinClient` puts their played mark, resume point and last-played date back with `UserItems/{id}/UserData` once the stop is reported, and Jellyfin's play count can't be put back), and outside queues the playlist's order gives Up Next, whose card says what it follows ("NEXT IN KIDS BEDTIME", "NEXT EPISODE", "NEXT IN THE COLLECTION": core `upNextHeading`). Each stop is told (`MediaServer.playStops`, `PlayStop`); `PlaylistPlaying.followStops` (started with the container) puts a sitting's stop in the playlist's record (`PlaylistRecords.stopped`: watched at 90%, else its resume point; where it carries on from), never a watch group's. So the rows stay apart: Continue Watching and Next Up are the user's own watching, Watching together the groups', and "Continue your playlists" the playlists' (each card is a playlist's place, `continueRow` from the records only: nothing asked of the server once the contents are kept); a title watched both ways shows in both. "Mark watched up to here" changes only the playlist's record. Spoilers: seen in any playlist counts as seen (`Spoilers.seenInPlaylists`, set at sign-in from the records). Packing a playlist for a trip takes what's left in it by its record (`PlaylistPlaying.remaining`). Watching in other apps (Jellyfin's web player) doesn't reach a playlist's record and marks titles watched for the user as before.
- Live TV: models and guide layout in `core/livetv` (`LiveChannel`, `TvProgram`, `Guide.cells`); Jellyfin calls in `core/jellyfin/JellyfinLiveTv.kt` (recording uses the server's own `Timers/Defaults` JSON); `LiveTvViewModel` shared; channels are `ItemKind.TV_CHANNEL` and play like any item.

## Where the code is

- `core/jellyfin/JellyfinClient.kt` is the client; Home's and libraries' row jobs, "Because you watched", resume/latest/query rows and Watching together are in `JellyfinRows.kt`, and the codec/format filtering index in `JellyfinCodecs.kt` (extension functions on `JellyfinClient`).
- Small answers shared rather than asked again (core `JellyfinClient`): stored preferences (`loadCustomPrefs`, e.g. the device index `nitrate-devices` that sign-in, backups and setup each read) for `PREFS_KEPT_MS` (1 min) per account, replaced by a save at once (a save still reads the server's copy fresh to round-trip it); the Companion's features (`companionHas`, 5 min, a failed ask not kept) for the rows as well; the user's watch groups for the rows (`featuresAndPartners`) for `TOGETHER_KEPT_MS` (30 s), let go on anything the app sends and replaced by every read of them. Library grids and Browse count the matches on the first page only (`enableTotalRecordCount` on `startIndex` 0; a later page gives -1, "keep the total", or where the list ends when it's short). Group standings and the Watching together row read a playlist's entries without descriptions, genres and tags (`titleItems`). A title the server answered 404 to (a shared playlist Jellyfin 12.4 lists but won't open by id) isn't asked again for `REFUSED_MS` (30 min, per account): `getItem` goes straight to the `/Items?ids=` lookup and `playlistItems` says `ItemUnavailable` without asking.
- Library pages keep their marks right (both apps): Browse (`BrowseViewModel`: a library's All and other tabs, every TV view) and the library grids (`LibraryGridViewModel`) hold their own pages of titles, so they follow `MediaServer.watchChanges` (the server's UserDataChanged as it's applied) and put each changed title's state on it where it is (app-core `viewmodel/GridMarks`: the states the server sent, else `userStates` for just those; a show or season whose episode changed elsewhere through `parentIds` then `userStates`). Nothing is reloaded or moved: a title marked watched on an Unwatched tab stays, with its new mark, until the page is opened again.
- Watch state shows quickly after a playback or a Watched press (both apps, core `JellyfinClient`): the "stopped" report is still sent in the background (the player closes at once), but it's kept as on its way, and a page reloading as the player closes (`RowsViewModel`'s refreshes, `DetailsViewModel.refresh`) first waits for it (`MediaServer.stopsSettled`, 3 s at most), so it reads what the playback did, not the state from before (it used to read the old state, then fix itself seconds later). Once the report or the Watched/Unwatched call is in, the title's state is read from the server (`userStates`, one small request) and said through `watchChanges` at once, marks and rows following the server's answer, never the app's guess; the server's own push repeating it a moment later isn't said again (`alreadySaid`, 5 s). A group play's stop waits (2.5 s at most) for the Companion to put the user's own state back, the server's pushes for that title held meanwhile (`restoring`), so it never flashes as watched in their own history. `AppContainer.serverChanges` lets a library scan's changes settle (1.7 s) but passes watch state straight on; pages reload 0.3 s after a change (was 2 s for both), and the change counters read before it are not reused.

- Details pages' "What it starts with" also has **Chat** (starting on the user's Group chat setting: Off, On, or an older thread to replay; the group's creator can start a new thread there) for a part in one of the user's watch groups, for the playback started from that page only (`docs/features/partners.md`).
